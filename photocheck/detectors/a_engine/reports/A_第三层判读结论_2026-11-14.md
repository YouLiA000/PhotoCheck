## 2. 范围缺口：31/38 张含姓名 / 地址 / 邮箱，全部未遮

这是本轮判读时暴露出来的、**不属于检测缺陷的问题**。

| 类型 | 含有的张数 |
|---|---|
| 地址（省市区路号） | **23** |

| 邮箱 | **10** |
| 以上任一 | **31** |
| 三者皆无 | 7（`dev-009/010/011/012/013/022/034`） |

### 2.1 根因不是漏检，是范围

```
契约 core/contract.py:  text -> ('phone', 'idcard')
C 的 dev 真值:          text/phone 31、text/idcard 11、meta/* 32、qr/* 10
                        —— 没有任何 name / address 对象
```

检测器根本没打算找它们，真值里也没有它们。所以：

- **按现行口径**：这是"设计如此"，不是欠遮，判读通过成立；
- **按"姓名/地址也算个人信息"的口径**：这 31 张全部欠遮，`dev-001` 这种
  同时有姓名、地址、证件号的图，只遮了证件号和电话。

### 2.2 一个具体例子（`image-dev-042`）

| OCR 块 | 是否遮 |
|---|---|
| `<姓名>`（姓名） | ❌ |
| `项目经理`（职务） | ❌ |
| `北辰数据`（单位） | ❌ |
| `<手机号>` | ✅ |
| `<邮箱>`（邮箱） | ❌ |
| `<地址>`（地址） | ❌ |

这张被判"合适"，是因为判读口径是"五类范围内"。**换成"个人信息"口径，它就是最严重的一张。**

**两个技术风险，已在原型里实测（见 `A_姓名地址原型验证_2026-11-14.md`）：**

1. **姓名误报率高**。上面 21 张里，"项目经理""北辰数据""中通速递"这类
   和真名在字形上无法区分，只能靠"是否紧邻收件人/寄件人"来判。
   而真实面单上职务、单位、姓名三行并列，邻接规则很容易连带误判。
2. **地址边界难以定义**。遮到完整门牌是清楚的，
   但遮不遮城市名？遮了会让图变得无法核对（用户看不出这是哪张单）；
   不遮则泄露了地域。这一条没有技术答案，是产品决策。
