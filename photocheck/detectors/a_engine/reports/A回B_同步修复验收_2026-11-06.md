## 3. 你 vendored 版的两个缺陷（已在主分支修掉）

### 3.1 数嵌套方块会被汉字击穿

`_finder_pattern_count()` 用 `findContours` 数"三级嵌套轮廓"，理由是定位符是三层结构。
它是，但**汉字 `回` 也是**：外框 + 空白环 + 内框，轮廓链和定位符一模一样。

实测（微软雅黑 44px，一张纯文字版面）：

```text
输入：返回 回收 回报 回执 / 回龙观 回民 回访 回头
你的 _finder_pattern_count → 16   （真定位符：0）
```

这意味着任意一块含 `回` / `田` 的文字，只要 cv2 给出候选四边形，门禁就会放行，
误报原样回来。C 的 dev 集里地址栏出现"回龙观"是完全正常的。

**主分支怎么改的**：不数形状，验签名。

1. **模块比 1:1:3:1:1**——过中心扫一行/一列，五段游程比例必须是
   外环 : 空白 : 3 模块实心核 : 空白 : 外环。这条对旋转不变（45° 时五段同比例放大 √2）。
2. **中心必须是暗的**——定位符中心是实心 3×3 核。`回` 的中心是空心的，白的，
   所以第 1 条根本起不了头。这一条才是真正的分水岭。
3. **排布**——三个定位符要构成等腰直角三角形且模块大小一致；文字造不出一致尺寸的直角三件套。

改完后的对照（`tests/test_qr_evidence.py` 里都钉住了）：

| 输入 | 修前计数 | 修后计数 |
|---|---|---|
| `返回 回收 回报 回执 / 回龙观…` | 16 | **0** |
| `田田田田…` | 8 | **0** |
| 真码 `express_001.png` | 3 | **3**（模块 6.6px ×3） |
| 导出图文字区 `[152,194,322,290]` | 0 | **0** |

### 3.2 `detectMulti` 解包错，多码图只出一个码

```python
ok, infos, points, _ = detector.detectMulti(gray)   # 4 个值
```

OpenCV 4.10 的 `detectMulti` 只返回 `(retval, points)` **两个值**，
`detectAndDecodeMulti` 才返回四个。所以这行每次都抛 `ValueError`，又被
`except Exception: ok, infos, points = False, (), None` 吞成"没找到码"——
**多码路径从头到尾没执行过一次**，一张图有两个码也只会报一个。

主分支先试 `detectAndDecodeMulti`，再退回 `detectMulti`，两种形状都处理；
新增回归 `test_multiple_codes_are_all_reported`（两个码的合成图必须报 ≥2）。
这条是我原来的 bug，不是你引入的，顺手一起修了。

## 4. 一个需要你确认的取舍

`finder_min_count=3` 意味着**半张码（只有 2 个定位符，比如码被裁到画框外）不报**。
规格卡 K-05 第 1 条要求"解不出也必须标框"，严格读的话这算违反。

我实测了一下：把真码裁到 55% / 65% / 75% 后，cv2 连候选四边形都不给，
所以 `min=1` 和 `min=3` 在这组样本上结果一样（都是 0 条），**这次的门槛取值没有造成
可测的漏检**。两个选项：

- 保持 3：精确优先，符合 C 的诉求（7 条误报降到 0）。
- 降到 2：`qr_evidence` 支持"两个定位符 + 水平对齐 + 模块大小一致"的判据（已实现并单测），
  能把"码被裁一半"捡回来，代价是多了 2 个定位符的放行面。

我倾向保持 3，等 C 的 dev 集里出现"半张码"真值再决定。请回一句你的意见。
