# T_ocr 的规模效应实测：为什么 1686 ms 与 5513 ms 差 3.2 倍

日期：2026-11-08
提出人：A
触发：C 在《给 B 合并说明》§7 报告"在 A 的 760×480 上 T_ocr 是 1686 ms，
在 C 的 1120×1560 上实测 5513 ms，是 W4 线的 2.7 倍，根因是测量对象不同（4.8 倍像素）"

---

## 0. 结论先行

1. **测量本身先出问题了**：同一张图、同一条命令，隔一天从 **1644.6 ms 变成 2845 ms（+73%）**。
   查下来 CPU 没降频（2900/2900 MHz）、负载 1%，但机器**正在用电池供电**。
   → 电源模式是此前完全没人记录的隐藏变量。
2. **所以"1686 vs 5513"这个对比不能只做内容归因**。它至少混了三个因素：
   内容（字符数）、硬件、电源状态。用绝对值互相比较在这里是无效的。
3. **像素不是主因**。控制变量实验显示：同尺寸下字符数 68→714（10.5 倍），耗时 1558→5783（3.7 倍）；
   同字符量级下像素 0.56→1.75 MP（3.1 倍），耗时只 +68%。有反例：
   **0.56 MP 的密集文字（5783 ms）比 1.75 MP 的稀疏文字（2624 ms）慢 2.2 倍**，
   按像素归一化会把这两张判反。
4. **建议放弃绝对值与像素归一化，改用参考集相对校准**（§6）：同一台机器、同一次运行里，
   先测一组固定参考图的耗时 `T_ref`，再用 `T_dev / T_ref` 判定。
   这样电源模式、CPU 型号、后台负载全部自动抵消。

---

## 1. 先说测量本身：同机跨日漂移 +73%

这条比数字归因更重要，因为**它让所有绝对值基线失效**。

| 时间 | 机器状态 | 样本 | T_ocr |
|---|---|---|---:|
| 2026-11-06 20:36 | 未记录（推测接电源） | 4 张合成图 | 1640.5 ms |
| 2026-11-07 20:07 | 未记录（推测接电源） | 10 张合成图 | 1644.6 ms |
| 2026-11-08 19:51 | **电池供电**（BatteryStatus=1，70%） | 同一张 `express_001` | **2841.4 ms** |
| 2026-11-08 19:51 | 同上 | 同图再测一次 | **2953.0 ms** |

排查过程：

```
tasklist  → 无残留 python 进程
CPU       → CurrentClockSpeed 2900 / MaxClockSpeed 2900（未降频），LoadPercentage 1%
电池      → BatteryStatus = 1（使用电池），电量 70%
```

**CPU 频率没有掉，负载是空的，唯一异常是电源状态。**
笔记本在电池模式下会限制 PL1/PL2 功耗墙，频率看着是满的，多核吞吐却大幅下降——
OCR 的 8 线程推理正好吃这个。

同一进程内连跑 6 次也能看到这个量级：`[5518, 2941, 2863, 2795, 2859, 2804]`，
冷启动那一发 5.5 s，稳态 2.8 s。

**结论：`FROZEN_BASELINE_T_OCR_MS = 1686.3` 这个数在今天这台机器上已经复现不出来。**
不是 OCR 变慢了，是测量条件变了，而此前没人把它写下来。

### 1.1 那 3.2 倍差在哪（粗略分解）

| 因素 | 量级 | 依据 |
|---|---|---|
| 内容（字符数） | ~1.6× | 我的样本 154 字符，C 的真实单据约 550 字符（§3 模型） |
| 电源/硬件 | ~1.65× | §1 的同机跨日对比 |
| 乘积 | ~2.6× | 接近观测到的 3.2× |

**两个因素都不小，所以不能把 3.2 倍全算到"像素 4.8 倍"上。**

## 2. 控制变量实验

固定文字内容与绘制方式，只改两个变量：画布尺寸、文字行数。
单进程预热后每例 5 次取 min（避免进程启动与换尺寸造成的冷启动）。

| 用例 | 像素 | 文字块 | 字符数 | 耗时 | ms/kchar |
|---|---:|---:|---:|---:|---:|
| 900×620 短文本 4 行 | 0.56 MP | 4 | 68 | **1558 ms** | 22917 |
| 900×620 长文本 16 行 | 0.56 MP | 16 | 714 | **5783 ms** | 8100 |
| 1120×1560 短文本 5 行 | 1.75 MP | 5 | 85 | **2624 ms** | 30871 |
| 1120×1560 长文本 20 行 | 1.75 MP | 20 | 500 | **5038 ms** | 10076 |
| `express_001`（我的基线样本之一） | 0.56 MP | 13 | 154 | 2789 ms | 18111 |

### 2.1 两个被单独观察到的效应

**像素效应（固定短文本）**：0.56 → 1.75 MP（3.1 倍），1558 → 2624 ms（+68%）。
→ 像素有影响，但远非线性。

**文字量效应（固定 0.56 MP）**：68 → 714 字符（10.5 倍），1558 → 5783 ms（3.7 倍）。
→ 影响大得多。

### 2.2 反例：像素归一化会判反

```
900×620  长文本：0.56 MP → 5783 ms
1120×1560 短文本：1.75 MP → 2624 ms
```

后者像素是前者的 **3.1 倍**，耗时却只有前者的 **45%**。
如果按 `ms / MP` 归一化，会把"更慢的那张"判成"更快"。

---

## 3. 三因子模型（拟合验证）

从上面 5 个点拟合出：

```
T_ocr ≈ 700 ms（固定开销）+ 840 ms × MP + 6 ms × 字符数
```

| 用例 | 模型预测 | 实测 | 偏差 |
|---|---:|---:|---:|
| 900×620 短文本 | 1578 ms | 1558 ms | +1.3% |
| 1120×1560 短文本 | 2680 ms | 2624 ms | +2.1% |
| 1120×1560 长文本 | 5170 ms | 5038 ms | +2.6% |
| 900×620 长文本 | 5454 ms | 5783 ms | −5.7% |

四个点都在 ±6% 内。**固定开销 ~0.7 s 是存在的**：哪怕只有 68 个字符也要 1.5 s，
因为检测阶段跑的是整图（双尺度 + 2× 上采样），与内容无关。

### 3.1 由此得到的判断

C 的 5513 ms 分解约为：

```
700（固定） + 1470（1.75 MP 检测） + ~3300（约 550 字符识别） ≈ 5470 ms
```

**看起来"像素导致的 3.2 倍"，实际是"真实单据的字数远多于我的合成样本"占了大头。**
我的合成图每张只有 150 字符量级，C 的真实单据约 500~600 字符。

## 4. 这也暴露了我自己的问题

`reports/基线表_v2.md` 里写的 **T_ocr = 1686.3 ms**，是在 10 张合成样本上取中位得到的。
这 10 张的特征是：**0.36~0.56 MP、2~13 个文字块、字符数 ≤160**。

它是一张"小图 + 稀疏文字"的基线。**用它 × 1.2 = 2023.6 ms 去卡真实单据，
等于用演示集的尺子量生产数据。** 这一点 C 说得对，我接受。

## 5. 建议：参考集相对校准（self-calibrating baseline）

### 5.1 为什么像素归一化不行

- §2.2 的反例会让它判反：0.56 MP 密集文字（5783 ms）比 1.75 MP 稀疏（2624 ms）慢 2.2 倍；
- 像素与耗时不是线性关系：3.1 倍像素只带来 +68% 耗时。

### 5.2 为什么绝对值基线也不行

§1 已经证明：**同一台机器、同一张图、同一条命令，隔一天能差 73%**，
唯一变量是电源模式。所以：

```
A 在电池模式测 2800 ms  ≠  C 接电源测 5513 ms 不是"内容差异"
```

任何"我测出 X ms，你也该在 Y ms 内"的写法都不成立，
除非两边同时锁定：机器型号、电源状态、后台负载、同批次样本。

### 5.3 推荐方案

```
每次验收，在同一次运行里先测一组固定参考图，得到 T_ref
判据：median(T_dev) / median(T_ref) ≤ K
```

参考集建议 3~5 张，覆盖小/中/大三种规模，随包分发（10~20 KB/张，成本可接受）。

好处：

| 问题 | 为什么被消除 |
|---|---|
| 电源模式 | 同一运行内，`T_dev` 与 `T_ref` 同比例受影响 |
| CPU 型号/核数 | 同上 |
| 后台负载 | 同上（前提是同一次运行） |
| 内容差异 | 参考集固定，`T_ref` 只反映"这台机器跑这套图要多久" |
| 规格卡没写测在哪 | 不再需要规定样本，只需规定"比值" |

`K` 的取值可以由现有数据反推：先各测 3 台机器 × dev 集，看 `T_dev/T_ref` 的分布，
取 P95 作为 K。

### 5.4 若三人不同意改协议，退而求其次

**在同一台机器上、同一次会话内，用同一批样本出基线**，并在报告里写清：

```
测量条件：CPU 型号 / 电源状态（接电源 or 电池）/ 后台负载 / 样本特征（MP、字符数中位）
```

这样至少让数字可复现。绝对值本身不是问题，**没写条件才是问题**。

### 5.5 需要 C 配合的两件事

1. **在 `image-dev-001` 上重测一次，并注明电源状态**——如果 C 那边也是电池模式，
   5513 ms 里有多少是内容、多少是电源，现在还分不开。
2. 提供 dev 38 张的**字符数中位数**（C 有 OCR 真值，统计一行代码），
   这样我这边能判断"内容差异"的份额。

## 附：复跑方式

样本由 `scripts/make_scale_samples.py` 现场生成，**不随包分发**
（4 张图 2.9 MB，比包里其余所有文件加起来还大；脚本里写清了构造方式，可完全复现）。

```bash
# 1. 生成控制变量样本
python scripts/make_scale_samples.py --out reports/t_ocr_scale

# 2. 逐尺寸测量（注意记录电源状态！）
python scripts/bench_ocr.py reports/t_ocr_scale --repeat 3

# 3. 单图复现本报告的关键数字
python scripts/bench_ocr.py reports/t_ocr_scale/dense_900x620.png --repeat 3
```

可复现性核对：我用该脚本重跑 `dense_900x620` 得 **5827.1 ms**（报告里是 5783.1 ms，差 0.8%），
说明 §2 那组数据本身是稳的——不稳定的是"机器状态"，不是实验设计。
