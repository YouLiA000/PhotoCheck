### 1.1 中文文件名（BC-0012）

```python
analyze("照片.png")   # 修复前：ContractError
                      # 修复后：image_id='img__-096763', width=64
```

根因：`image_id` 直接取 `Path(path).stem`，而契约只允许 `[A-Za-z0-9_.:-]` 且必须以字母数字开头。
照片来自手机和微信，文件名天然带中文、空格、括号、下划线——所以这不是边角情况。

修法三个细节（都补了测试）：

1. 发生过替换就追加 6 位 CRC32 后缀，否则 `照片` 和 `合同` 会塌缩成同一个 `__`；
2. **截断本身也触发后缀**，否则 `x*300` 与 `x*301` 会截成同一个 id；
3. **显式传入的 `image_id` 保持严格**，非法仍抛 `ContractError`——那是调用方的承诺，
   静默改写会把对方的 bug 藏起来。

覆盖用例：`照片 测试(1).png`、`IMG 1234.JPG`、`_DSC0001.JPG`、`3月账单.png`、
emoji、300 字符超长名。19 条测试。

### 1.2 关于"包 SHA-256 写入 README"（第 3 条）：需要改法

这条要求存在自指：README 在包内，把 zip 的哈希写进 README，zip 的哈希就变了。

我的做法是拆成两个哈希，都写进 README 的「版本与校验」块（构建时自动生成，不手写）：

| 哈希 | 位置 | 为什么放这儿 |
|---|---|---|
| **源码树哈希**（`core/` `scripts/` `tests/` 全部 `.py`，路径有序） | **README 内 + `VERSION.json`** | 只覆盖代码，写文档不会改变它，不会自指 |
| **交付包 SHA-256** | 包外 `<包名>.zip.sha256` | 写进包内必然自指 |

校验：

```bash
python scripts/build_delivery.py --check-hash
# recorded: 4FC93DED...
# current : 4FC93DED...
# MATCH
```

这样"代码版本"能自证，"包本身"能在包外核对。如果你们要求 README 里必须出现 zip 哈希，
我建议改成一个固定格式的构建号（如 `20261107-2044-4FC93DED`），语义等价且不自指。
