## 三、先后顺序：按依赖排，不按卡号排

### 第 0 步（开工前，三人一起，半天）

把契约 v4 的五个记录（ImageDescriptor / Detection / Decision / RedactionPlan / VerificationReport）落成一份 JSON Schema 和 `validate_records()`。
**这是唯一的真阻塞点**——接口不定，三个人写出来的东西接不上。之后任何改动都要三人同意。

### 主线（关键路径）

```
契约 v4 定稿
   ├─ B: K-01 载入 → K-02 重建导出          ← 第 1–2 周，能独立验证（exiftool 前后对比）
   ├─ A: K-05 二维码检测解码                 ← 第 1–2 周，2 人日，最快拿到"遮了还能不能解"的实验
   └─ C: R-01 标注指南 + K-13 建集 + K-11 骨架（mock 数据）  ← 第 1–4 周
        ↓
   A: K-03 OCR → K-04 敏感实体（第 3–5 周）
        ↓
   B: K-08 区域处置 ← 吃 A 的 Detection（第 6–7 周）
        ↓
   B: K-09 复检（W2 起四次增量：EXIF → OCR → 二维码 → 人脸，第 8 周汇总）
        ↓
   C: K-11 接真数据 → K-13 三层评测脚本 → A: R-02 基线表
        ↓
   B: K-14 离线验证 + K-15 集成打包
```

### 为什么 A 先做 K-05 而不是 K-03

K-05 只要 2 人日，且能一次性回答最关键的问题（「实心遮盖后二维码是否 100% 解不出」）。K-03 要 3 人日且是全线最慢的一环，先做它会让前两周没有任何可演示的东西。

## 四、三条硬规则

**1. 接口一人一主，别人不改**

| 记录 | 定义方 | 消费方 |
|---|---|---|
| ImageDescriptor | B（K-01 产出） | A、C |
| Detection | A（K-03/K-04/K-05/K-06/K-07 产出） | B、C |
| Decision | C（K-11 界面产生） | B（K-08 消费） |
| RedactionPlan | B（含手动补框） | B（K-09 复检） |
| VerificationReport | B（K-09 产出） | C（K-12 展示） |

改自己那份要发 PR；改别人的，先改双方共同遵守的 Schema。

**2. 分支与评审**

`main` 保护；每人 `feat/<角色>-<卡号>`；PR 必须由另一个角色 review（A↔B 互审，C 的 PR 由 A 或 B 看）。
理由：三人都在入门阶段，自己写的 bug 自己看不出来。

**3. 每周五冒烟测试**

一条命令跑「一张图 → 出 VerificationReport」。红了下周优先修，不加功能。这条对应规格卡 K-15 的验收。

## 六、时间不够先砍哪块

| 投入 | 团队总 P0（30.0 人日） | 个人最长杆 | 结论 |
|---|---|---|---|
| 12 小时/周（1.5 人日/周/人） | 6.7 周 | B 7.7 周 | P1 全保，K-07 人脸可做 |
| 6 小时/周（0.75 人日/周/人） | **13.3 周**，正好贴 W14，零缓冲 | **B 15.3 周 → 超期** | 见下 |

6 小时线下必须卸货的顺序：

1. **B 把 K-15 集成打包（2.0）转给 C** → B 降到 9.5 人日（12.7 周），C 升到 11.0（14.7 周）。打包与评测脚本、复现包天然同一套环境，转过去阻力最小。
2. **A 不做 K-06 / K-07**（省 2.3 人日）。人脸降级为手动补框——规格卡本来就允许，K-09 的人脸项记 `not_applicable`，按三检验收。
3. **R-03 / R-04 / D-01 / D-02 全部砍掉**，只保 R-01、R-02、R-05。

> 这正是规格卡 4.1 与申请书「每人每周 4—6 小时」的口径差必须在这周定死的原因：它直接决定 K-07 存不存在、B 要不要转包。
