## 0. 一句话说明

这是一套**可运行的评测与标注底座**：能校验契约记录、能接口径一致地算检测质量、能用 60 张合成样本
演示完整交互（检测框 → 逐个决定 → 补框 → 导出交接包 → 结论面板），并且自带 183 条测试与 40 项
自动审计来证明它没坏。

**它不是检测器。** 检测器是 A 的 K-03/04/05，处置是 B 的 K-08/09，两者尚未交付，`src/` 为空。
所以现在演示时"检测结果"来自**数据集的真值**（真值本身就是合法的契约 v4 `Detection`），
而不是来自 OCR。这一点必须提前讲清，否则会被误读成"检测效果就是 100%"。

## 4. 验收：五条命令，逐条给期望输出

```bash
# ① 契约：一条完整闭环必须通过
python contract/validate_records.py contract/examples/valid_pipeline.json
# 期望：校验 10 条记录：0 个错误，0 个警告

# ② 评测自测：拿真值当预测，指标必须全 1.0
python eval/eval.py --set dev --perfect
# 期望：TP 84  FN 0  FP 0  类别判错 0；召回 1.0 精确 1.0；✓ 自测通过

# ③ 用一份"有缺陷的预测"验证指标会动（可复现）
python eval/eval.py --set dev --pred-dir <你造的预测目录>
# 期望：不合契约 / image_id 对不上时退出码 2，并打印具体文件名与改法

# ④ 锁定集未被改动
python dataset/tools/seal_lock.py verify
# 期望：lock 集完好：49 个文件，与封存记录一致

# ⑤ 全量冒烟
python tools/smoke.py
# 期望：8 项全过，约 50 秒
```

> **首次解压后跑 `audit/run.py`，结果应为：36 PASS / 2 SKIP / 2 FAIL（C 36/38）。**
> 2 项 SKIP 是 `EV-02`、`PV-02`——还没有 `results/`。跑一次
> `python eval/eval.py --set dev --perfect`（不带 `--out`）就会生成默认产物，随即变成
> **38 PASS / 0 SKIP / 2 FAIL（C 38/38）**。
> 2 项 FAIL 始终存在，是 A 的 `DET-01` 与 B 的 `RD-01`，与本套交付无关。
> 这个「36→38」的过程已在交付包上实测过，不是推测。

**用真实预测检查时**（A 交付后）：

```bash
python eval/eval.py --set dev --pred-dir <A的输出目录>
# 目录里每个文件必须叫 <image_id>.json，文件内记录的 image_id 必须与文件名一致。
# 不一致会直接退出码 2——这是有意的：错位会静默出 0 分，比报错难查得多。
```

产物在 `results/<时间戳>-<git短sha>/`：`detection_quality.csv`、`detection_by_difficulty.csv`、
`failure_cases.csv`、`redaction_validity.csv`、`over_redaction.csv`、`summary.json`、`README.md`。
后两张表结构就位但标注「未接入」——它们的输入还不存在，塞假数比空着更糟。

## 6. 已知缺口（写报告时必须交代，不要当成已完成）

1. **没有检测器。** 当前所有"检测结果"都是数据集真值。任何"召回 100%"的说法只证明**评测代码没错**，
   不证明检测效果。
2. **合成样本偏容易。** 无拍摄角度、文字偏清晰、不含人脸、负例是设计出来的 → dev 上的指标偏乐观。
