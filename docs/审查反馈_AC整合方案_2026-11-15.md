## 一、总体结论

## 二、问题清单（按严重程度）

### P0-1｜`1686.3 ms` 不是新参考集的基线（事实错误）

**位置**：§2.1「冻结基线 T_ocr = 1686.3 ms（K-03 参考集，AC 供电…）」；
§2.2「冻结基线 1686.3 ms 的样本形状是 0.36 MP / 91 字符」；
§2.3 闸门直接用它算 2023.6 / 2529.5。

**问题**：`1686.3 ms` 来自 B 之前的 **10 张旧样本**（0.36–0.56 MP、≤160 字符），
不是方案 §2.2 要新建的 5 张参考集。新参考集尚未生成、未测量、未冻结。
把它写成「K-03 参考集」的基线，是把**旧集的数**贴到**新集的名**上。

**后果**：签字后若 A 按新 5 张测出 1900 ms，闸门会立刻变成
「旧基线卡新集」，谁对谁错说不清。

**建议**：

- 把 1686.3 明确标为 **「旧基线 / 预验收参考值」**，不写「K-03 参考集基线」；
- 新参考集测出后，用**新值**替换 `T_ocr_ref`，并记录版本（如 `T_ocr_ref v2 = …`）；
- 在替换前，§2.3 的闸门只能用于「预验收」，不能写进最终报告；
- 方案里加一句：「新参考集未冻结前，K-03 不产生最终验收结论」。

### P0-2｜`p95` 的统计单位未定义（口径漏洞）

**位置**：§2.1.3「每张图至少跑 3 次，每图取中位数」；
§2.1.5「报告 median、p95、max、n」；§2.3 `p95_dev ≤ 1.5 × T_ocr_ref`。

**问题**：`p95` 是按 **30 个「每图中位数」** 算，还是按 **90 次原始运行** 算？
两种算法结果不同：

- 按每图中位数：n = 图数，p95 接近「第二慢的图」，对单图长尾敏感；
- 按全部运行：n = 3×图数，p95 更平滑，但同一张图的 3 次不独立。

**后果**：同一批数据，两种算法可能一个过、一个不过；而方案没有规定用哪种。

**建议**：

- 明确 **p95 以「每图中位数」为单位，n = 有效图数**；
- 同时报告「图内 3 次的极差中位数」，用来显示单图波动；
- 在报告模板里写死字段名（如 `p95_of_image_medians`），避免口头歧义；
- 若担心 n=30 时 p95 不稳，加 bootstrap 95% CI，而不是换算法。

---

### P0-3｜K-09「缺失 check」与「环境不可用」仍会碰撞（逻辑边界）

**位置**：§5.1 表格「计划区域没有 check → 缺失 → failed」与
「检测器客观不可用，未执行检查 → not_applicable → pending」；
§5.2「存在缺失 check / not_run → failed」；§5.3.3「环境不可用写 `a_ocr_unavailable`，status=`not_applicable`」。

**问题**：如果实现「环境不可用」时**不写 check**，它会落入「缺失 → failed」，
而不是方案想要的 pending。表格里「未执行检查 → not_applicable」与
「没有 check → failed」字面上就是矛盾的——区别只在「有没有写那条 check」。

**后果**：B/C 两人对「检测器没装」的处理可能一个判 failed、一个判 pending，
而这正是 K-09 想消除的分叉。

**建议**：

- 明确一条硬规则：**环境不可用也必须写一条 `status=not_applicable` 的 check**；
  **没有 check 一律按缺失判 failed**，不允许用「没写」表示「不可用」；
- 在 §5.1 表格把「未执行检查」改成「已写 `not_applicable` check（环境不可用）」；
- 加两条回归：`a_ocr_unavailable` → pending；`plan item 无对应 check` → failed。

### P1-1｜K-03 闸门是「5 张参考集标量」对「38 张 dev 分布」，缺形状分层

**位置**：§2.2 参考集 5 张、§2.3 `median_dev / p95_dev`。

**问题**：`T_ocr_ref` 是 5 张图的**等权中位数**，dev 是另一套形状分布
（1.4 MP 稀疏为主）。用单一标量卡一个分布，形状变化会被误读成性能变化。

**建议**：

- 报告里同时给 dev 的**像素/字符数中位数**（方案已有）与**分档中位数**
  （如 ≤0.6 MP / 0.6–1.5 MP / >1.5 MP）；
- 明确「闸门是回归检查，不是形状归一化模型」；
- 若 dev 形状分布发生版本变化，必须同时报新旧分布，不能只比 median。

### P1-2｜A 的 `1885.0 / 2521.2 / 2873.9` 缺 n 与图集，`8 ms` 论证不可比

**位置**：§2.4。

**问题**：这三个数没有写 n、图集、像素/字符中位数；而 §2.4 自己说
「尚未使用固定参考集，A/C 旧基线形状不一致」。既然不可比，
就不能用「只余 8 ms」来论证「不能提前放宽 p95」——8 ms 的差距本身不可信。

**建议**：

- 补 n、图集、电源、像素/字符中位数；
- 把「8 ms」改写成：「在**旧口径**下只余 8 ms，说明旧数字不能作为放宽依据；
  必须按新参考集重测后再决定」——结论不变，但论证成立。

### P1-4｜`failed` 但无 residual、也无「哪块缺失」的记录

**位置**：§5.1「计划区域没有 check → failed」；§5.2 汇总规则。

**问题**：缺失 check 时，报告里既没有 failed check，也没有 residual
（契约的 `failed_check_without_residual` 只约束「failed 的 check」）。
结果是：`disposal_state=failed`，但 `residuals=[]`、`checks` 里也没有那块区域，
消费者无法知道**哪块没查**。

**建议**：

- 报告里增加 `missing_regions`（或把缺失项写成一条 `status=not_run` 的 check，
  这样它就不再是「缺失」，而是「明确未执行」）；
- 若选后者，§5.1 的「缺失 → failed」就可以简化为「`not_run` → failed」，
  同时解决 P0-3 的边界；
- 加一条回归：缺失区域必须在报告里可定位。

### P1-5｜`method` 承载错误原因，语义被重载

**位置**：§5.3.2「错误原因写进 method，如 `a_ocr_probe_error`、`a_qr_probe_timeout`」。

**问题**：`method` 的语义是「用什么手段复检」，不是「为什么失败」。
把 `*_error` / `*_timeout` / `*_invalid` 塞进去，会让按 method 聚合的报表
（如「OCR 复检通过率」）把错误项算成另一种手段。

**建议**：

- 短期：规定 `method` 只写手段（`a_ocr_probe`），错误原因写进**新的 `reason` 字段**
  或 `method` 的固定前缀约定（如 `a_ocr_probe@error`），并在消费端统一解析；
- 中期：契约加 `reason`（枚举：`ok` / `timeout` / `exception` / `empty` / `invalid` / `unavailable`），
  `method` 保持稳定；
- 如果暂时不加字段，至少在方案里写清「method 是复合字段，格式为 `<method>[_<outcome>]`」，
  别让下一个人猜。

### P2-5｜端到端延迟无人负责

避免用户感知延迟成为盲区。
