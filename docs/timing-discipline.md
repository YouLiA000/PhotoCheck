# T_ocr 的测量纪律（2026-11-08）

> 这份文档不是改判据，是改**测法**。判据（W4 线 = 基线 × 1.2）不动。

## 1. 为什么写这份

2026-11-07，C 报「`image-dev-001` 上 T_ocr 5513 ms，是 W4 线的 2.7 倍，
根因是测量对象不同（4.8 倍像素）」。A 因此做了一轮控制变量实验（见
`T_ocr_规模效应实测_2026-11-08.md`），结论是"字符数才是主因"。

2026-11-08 复核发现：**两边都不是主因，真因是冷启动。**

| 口径 | C 的机器（Ryzen 9 8945HX，**接电源**） |
|---|---:|
| 新进程**首次** `analyze` | **6643 ms**（另一次 5781 ms） |
| 预热后 纯 OCR | **1678 – 1726 ms** |
| 预热后 OCR + QR | 1858 – 2054 ms |
| 预热后 OCR + QR + 人脸 | 1890 – 1989 ms |
| 仅 QR / 仅人脸 | 173 ms / 49 ms |

A 的报告里贴过同一现象：`[5518, 2941, 2863, 2795, 2859, 2804]`，
首发 5518 与 C 的 5513 是同一件事。

**所以 5513 ms 既不能代表 OCR，也不能代表稳态。它代表"从没跑过的进程第一次跑"。**

## 2. 一个测量错误，两次返工

| 时间 | 谁 | 结论 | 对不对 |
|---|---|---|---|
| 11-07 | C | 像素 4.8 倍导致 2.7 倍 | ❌ 是冷启动 |
| 11-08 | A | 字符数 550 是主因 | ❌ 实测 dev 中位 64.5 字符 |
| 11-08 | C（本次） | 冷启动；同图对照（`express_001`）稳态 1211 ms | ✅ |

两次都错在**没规定测法**，而不是谁不认真。规格卡 K-03 只写了阈值，
没写"怎么测"——这是它的漏洞。

## 3. 四条纪律（建议作为 S-7 提交表决）

```
1. 必须预热：正式计时前至少跑 1 次同类调用，那一发不进统计。
2. 报中位数，n ≥ 3；不报单次，不报均值（OCR 耗时右偏，均值被抖动拉走）。
3. 报告必须写测量条件：CPU 型号 / 电源状态（接电源 or 电池）/ 样本 MP 与字符数中位。
4. 冷启动如需报告，单独列一栏，注明"含模型加载"，不与稳态混在一起比较。
```

**不改阈值，不用改协议，可以立刻执行。**

## 4. 为什么不需要"参考集相对校准"

A 建议在同一次运行里先测固定参考图，用 `T_dev / T_ref` 判定。理由充分（能抵消电源、CPU、负载），
但**数据不支持它有必要**：

**同一张图**放两边跑才是有效对照（不同图比出来的"差 0.5%"是巧合）：

| 对照 | 图 | 纯 OCR 稳态 |
|---|---|---:|
| A 的冻结基线 | 合成样本中位（0.36–0.56 MP，≤160 字符） | 1686.3 ms |
| C 复现同一张 | `express_001`（0.558 MP / 154 字符） | **1211 ms** |
| C 的 dev 最大图 | `image-dev-001`（1.75 MP / 143 字符） | 1678 – 1734 ms |

同图上 C 比 A 快 28%——**基线偏保守，不会误伤**。引入参考集会让每个交付包多带 3–5 张图、验收脚本多一步，
而带来的精度提升在 2% 以内——**不如把"预热 + 中位 + 写条件"这三件事做到位**。

如果将来出现 >20% 的跨机器差异，再上参考集也不迟。

## 5. 工具

`tools/bench_detect.py`——默认只报稳态，冷启动必须显式要求：

```bash
# 稳态（预热后，三次取中位）
python tools/bench_detect.py dataset/dev/images/image-dev-001.jpg --repeat 3

#  测量条件：电源 AC, battery 100%　重复 3
#  [1/1] image-dev-001.jpg  纯OCR 1726 ms  +QR 1858  +人脸 1890  1.747 MP 143 字符

# 冷启动（对照用，单独一栏）
python tools/bench_detect.py dataset/dev/images/image-dev-001.jpg --cold
#  [1/1] image-dev-001.jpg  冷启动 6643 ms  1.747 MP 143 字符

# 整个目录 + 落盘
python tools/bench_detect.py dataset/dev/images --limit 10 --json bench.json
```

设计上有意让**错误测法需要主动选择**（`--cold`），而不是默认踩进去。

## 6. dev 集的规模特征（给做性能判断的人）

38 张有效样本实测：

| 统计量 | 值 |
|---|---:|
| 字符数中位 | **64.5**（均值 81，范围 19–143） |
| 文字块中位 | 10 |
| 像素中位 | 1.4 MP |

**这些样本是稀疏排版**（标签 + 一个号码），不是密集发票。
任何"按字符数外推到真实单据"的估算都要考虑这一点——真实快递面单的字数会显著更高。

逐张数据：`docs/dev_chars_2026-11-08.json`。

## 7. 结论

```
W4 线       = 1686.3 × 1.2 = 2023.6 ms
C 实测稳态  = 1678 – 1726 ms   →  达标
C 实测冷启动 = 6325 – 6643 ms  →  这是启动成本，不该按检测能力评价
```

**T_ocr 达标，不需要改判据，不需要按像素归一化。**
之前两次"超标"结论都是测量方法造成的。
