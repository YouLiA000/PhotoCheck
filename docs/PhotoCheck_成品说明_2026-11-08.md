# PhotoCheck · 照片隐私体检 —— 成品说明

> 一个可以拷到任何 Windows 电脑上直接运行的本地应用。
> 本文回答五个问题：**选题是什么、用了什么技术、需要什么环境、界面怎么设计、怎么演示**。
> 配套：`docs/照片隐私体检_面试演示脚本.md`（照着念的五分钟流程）

---

## 一、选题与核心功能

### 1.1 一句话

**给照片做一次"隐私体检"：找出里面的手机号、身份证号、二维码、人脸，以及看不见的拍摄信息，
帮你擦干净，并且**证明它真的擦干净了**。**

### 1.2 为什么选这个题

| 理由 | 说明 |
|---|---|
| 问题真实 | 发快递单、发名片、发聊天截图，几乎每个人都在无意中泄露手机号和住址 |
| 技术有层次 | 不是"调个 API"，而是 OCR + 二维码解码 + 人脸检测 + 规则校验 + 图像处理 + 复检，六段串起来 |
| 有硬骨头 | 「擦掉」容易，「证明擦干净」难——这是本项目最有分量的部分 |
| 能讲清边界 | 不吹"绝对安全"，只陈述"我验证到了哪一步"，这在面试里比吹牛加分 |

### 1.3 五个核心功能

| # | 功能 | 用户看到什么 |
|---|---|---|
| 1 | **文字敏感信息** | 手机号（含 `+86` / `0086-` 三种写法）、身份证号（末位 X、校验位三态） |
| 2 | **二维码** | Wi-Fi 密码、名片、收款码、普通链接——**解出内容才判类型**，不是见到方块就报 |
| 3 | **人脸** | 可见人脸区域（MediaPipe） |
| 4 | **拍摄信息** | GPS 坐标、拍摄时间、机型、处理软件、内嵌缩略图——这些在图片"里面"，肉眼看不见 |
| 5 | **处置与复检** | 勾选要擦的内容 → 生成脱敏副本 → **逐区域回读校验** + 整图重扫 |

### 1.4 和同类工具的区别（面试可以强调）

| 常见做法 | 本项目 |
|---|---|
| 打码后直接保存，不验证 | **擦完再读一遍**：把遮盖区重新 OCR / 重新解码，确认读不出来 |
| 只处理看得见的区域 | 额外做**整图重扫**，抓"计划外的残留" |
| 元数据（GPS）完全不管 | 元数据**始终整图清除**，并用 ExifTool 独立复核 |
| 输出"已安全" | 输出 `passed / pending / failed` 三态，`pending` 明确写"这一块没法语义确认" |

## 二、技术栈

### 2.1 分层

| 层 | 选型 | 为什么是它 |
|---|---|---|
| 文字识别 | **RapidOCR**（ONNX Runtime） | 纯 CPU、无需 GPU、模型小；不依赖 Paddle，装起来不折腾 |
| 二维码 / 条码 | **OpenCV QRCodeDetector + pyzbar** 双后端 | 两个后端互补：一个擅长整图定位，一个擅长小码与条码 |
| 人脸 | **MediaPipe**（0.10.14） | 正脸够用、CPU 实时；不引入 torch |
| 号码判定 | **正则 + ISO 7064 MOD 11-2 校验** | 硬规则，可解释；身份证号还带**生日段合法性**门禁 |
| 数据契约 | **JSON Schema（v4）+ 自研校验器** | 三个人协作，字段必须能机器校验，否则一定漂移 |
| 图像处置 | **Pillow + OpenCV**（纯色 / 模糊 / 马赛克） | 三种手法覆盖不同需求；纯色最稳 |
| 元数据清除 | **Pillow + ExifTool** | 清除用代码，**复核用独立工具**——自己清自己验不算数 |
| 服务端 | **Python 标准库 `http.server`** | 零框架依赖，少一层就少一个装不上的理由 |
| 前端 | **原生 HTML / CSS / JS** | 无构建步骤、无 npm、无框架；界面能完全按产品需要做 |
| 打包 | **便携解释器 + 目录复制** | 见 §3.2，不用 PyInstaller 是刻意的 |

### 2.2 一次处理的数据流

```
图片
 │
 ├─► 载入（Pillow）──► 元数据 → GPS/时间/机型/软件/缩略图（5 类）
 │                      └─► 描述符（尺寸、方向、坐标空间）
 │
 ├─► 检测（A 的引擎）
 │     ├─ OCR → 文字块 → 正则 + 校验 → 手机号 / 身份证
 │     ├─ 二维码 → 解码 → 内容分类 → Wi-Fi / 名片 / 收款 / 链接
 │     └─ MediaPipe → 人脸框
 │
 ├─► 决定（用户勾选）→ Decision(redact / retain)
 │
 ├─► 计划（Plan）→ 要擦的区域清单（含手动补框）
 │
 ├─► 处置 → 纯色 / 模糊 / 马赛克 + 元数据整图清除 + 重编码
 │
 └─► 复检（B 的验证器）
       ├─ 逐区域：把遮盖区单独读一遍（OCR 复检 / 二维码复检）
       ├─ 整图重扫：有没有计划外的残留
       └─ ExifTool：元数据是不是真的没了
            │
            └─► 报告：passed / pending / failed + 逐项明细
```

### 2.3 打包与发布方式

**选择：把「能跑的解释器 + 装好的依赖」整目录复制，而不是 PyInstaller 单文件。**

| 方案 | 问题 |
|---|---|
| PyInstaller | onnxruntime / mediapipe / opencv 的动态库与资源靠 hook 收集，版本一换就漏；**漏了的表现是"换台电脑打不开"**，正是现场最难救的故障 |
| 要求目标机装 Python + pip install | 违背"不依赖开发环境"，而且要联网 |
| **目录复制（采用）** | 体积大（474 MB），但**可预测**：开发机上跑通，拷过去就能跑 |

产物结构：

```
PhotoCheck_App/
    启动.bat              ← 双击
    自检.bat              ← 打不开时先跑这个
    使用说明.txt
    runtime/              ← 便携 Python 3.11.9 + 依赖 + ExifTool
    app/                  ← 代码 / 界面 / 示例图
```

**裁剪**：从 1.2 GB 的完整环境裁到 474 MB，去掉的是
Gradio 全家（界面改成原生 HTML）、JAX / SciPy（只走 MediaPipe 的 solutions 老接口，实测不需要）、
pandas、打包工具自身。**每次构建都会实跑自检与端到端检测**，裁错了会立刻暴露。

## 三、系统环境与依赖

| 项 | 要求 |
|---|---|
| 系统 | Windows 10 / 11，64 位 |
| 内存 | 4 GB 以上（峰值约 1.2 GB） |
| 磁盘 | 1 GB 空闲 |

> 已在 Windows 10 x64 上验证：从任意目录调用内置解释器，自检 15 项全绿，
> 端到端检测 1000×1400 图约 4.5 秒。

### 3.2 内置依赖（全部随包）

```
numpy 1.26.4 · opencv-contrib-python 4.10.0.84 · onnxruntime 1.31.1
rapidocr-onnxruntime 1.4.4 · mediapipe 0.10.14 · Pillow 10.4.0
pyzbar 0.1.9 · piexif 1.1.3 · jsonschema 4.26.0 · shapely · pyclipper

```

### 3.3 启动

1. 解压 `PhotoCheck_App_win64.zip`
2. 双击 **`启动.bat`**
3. 浏览器自动打开 `http://127.0.0.1:7861/`（端口占用会自动顺延）
4. 关闭黑色命令行窗口即退出

> 首次点检测会多等 3–5 秒（加载 OCR / 人脸模型），之后每张 2–5 秒。

## 四、界面与交互设计

### 4.1 布局：三栏，对应"来源 → 检查 → 决定"

```
┌──────────────┬───────────────────────────┬──────────────────┐
│  示例图库     │        图像舞台            │    发现项清单      │
│  上传照片     │   检测框叠加 / 前后对比     │    遮盖方式        │
│  它查五类     │   图例 / 耗时              │    复检报告        │
└──────────────┴───────────────────────────┴──────────────────┘
```

**为什么这么分**：左边是"从哪来"，中间是"看到了什么"，右边是"要我决定什么"。
用户的操作视线是一条从左到右的直线，不需要在两个标签页之间来回找。

### 4.2 四个关键交互

| 交互 | 设计 | 为什么 |
|---|---|---|
| **检测框颜色 = 风险等级** | 红 / 橙 / 灰 三档 | 不写"高风险"三个字也能一眼看出轻重 |
| **勾选 = 擦，取消 = 留** | 取消后框变灰虚线 | 直接在图上看清"这一块我不擦"，比纯列表直观 |
| **对比滑杆** | 左右拖动看原图 / 处理后 | 打码效果必须"看得见"，否则用户不敢用 |
| **手动补框** | 开关打开后在图上拖一个矩形 | 检测一定会漏（手写、艺术字、遮挡），必须给用户兜底手段 |

**手动补框的完整操作**——这是唯一的兜底手段，演示时要留 40 秒讲它：

1. 选一张图，等检测结果出来（**只在「检测」视图可用**，右上是按钮所在）
2. 点「手动补框」→ 按钮变紫、鼠标变十字
3. 在图上**按住左键拖出一个矩形**，松开即生成（小于 8×8 像素的会被忽略）
4. 可连续拖多个：按钮文字变成 `手动补框 · 2`，旁边出现「撤销」「清空」
5. 点「生成脱敏副本」——**补的框要走到这一步才真的涂掉**，只画不生成等于没做

补出来的框是**紫色虚线**，和检测框（实线）在视觉上分开。想删单个框，**直接点它**。
切换图片会清空全部补框——不同图上的坐标没有意义。

**什么时候该用它**（按实际踩到的频率排）：

| 场景 | 为什么必须手动 |
|---|---|
| 拍屏幕的二维码 | 摩尔纹让码解不出，检测器不报，但码还好好地留在图上 |
| 手写号码 | 识别率明显低于印刷体，`real-014` 就漏了一个 |
| 证件号被遮挡 / 艺术字 | 校验位算不出来，规则不敢报 |
| 人脸侧脸 / 口罩 | MediaPipe 只认正脸 |

**不要**用它替代"没检出"的排查——先看是不是图本身的问题（模糊、过曝、摩尔纹），
补框是兜底，不是常规操作。

### 4.3 状态三态的语言

| 状态 | 界面写法 | 含义 |
|---|---|---|
| `passed` | 通过（绿） | 每个计划区域都回读确认过，整图也没有计划外残留 |
| `pending` | 部分待确认（黄） | 有一块**无话语义复检**（例如手动补的区域），不假装通过 |
| `failed` | 未通过（红） | 回读仍能读出内容——例如**模糊半径不够**，字还能被 OCR 认出来 |

> 「模糊会判失败」不是 bug。演示时可以现场选模糊，让面试官看到红字，
> 然后解释："它没有骗我，这块确实还能被读出来。"

### 4.4 三个「不让人误判」的设计（2026-11-08 修正）

第一条是真 bug 修出来的：

| 设计 | 起因 | 做法 |
|---|---|---|
| **遮盖框先合并再外扩** | 引擎把一个号码读成两块（`139-1234-` 与 `5678`），逐个遮盖后**中间留了一条缝**，导出图上能直接看到 `-56` | 同值/紧邻的同 subtype 框先合成一个，再外扩 3–8%（封顶到图内）。宁可多盖，隐私工具不存在"盖太多" |
| **默认看「处理后整图」** | 对比视图左半边是原图，用户以为"二维码盖了、手机号没盖" | 生成后默认进「处理后」，对比改为可选标签页，并标注"左侧=原图" |
| **没检出码就明说** | 拍屏幕的二维码因摩尔纹解不出，检测器不会报，图上却留着一个完好的码 | 复检报告里加一条「未检出二维码 · 需人工确认」，并提示用「手动补框」 |

这三条的共同点：**宁可承认"这块我没处理"，也不让人以为全都干净了。**

### 4.5 报告能带走、文件能找到

生成之后，右栏底部有三个动作：

| 动作 | 作用 |
|---|---|
| **下载报告（TXT）** | 一页人读版：状态、逐区域复检、整图重扫、导出哈希 |
| **JSON** | 机器版，字段与接口一致，便于二次处理或归档 |
| **在文件夹中显示** | 直接弹出资源管理器定位导出文件（本地程序才做得到） |

**为什么报告要落盘**：截图不能当凭证。把图片和报告一起交出去（交给同事、交给客服、
作为投诉材料），别人才可能核对"擦了什么、验到哪一步"。只活在浏览器里的数字，关掉就没了。

三份产物都在 `work/outputs/run-xxxx/` 下：脱敏图 + `report.txt` + `report.json`。

### 4.6 「有些号码没被框出来」是规则边界，不是漏检

演示时最容易被追问的一句。`demo-01` 那张登记表上有五行号码，只框了三行：

| 行 | 内容 | 剥掉区号后 | 为什么 |
|---|---|---|---|
| 国际号码 | `+86 177 2970 2814` | 11 位、首位 1 次位 7 | ✅ 框 |
| 备用号码 | `0086-163 4859 7822` | 11 位、首位 1 次位 6 | ✅ 框 |
| 传真号码 | `+86 185…`（紧邻写法） | 11 位 | ✅ 框 |
| — | `+86 747 4628 350` | **10 位、首位 7** | ❌ 不是手机号 |
| — | `0086-9878 9701 0405` | **12 位、首位 9** | ❌ 不是手机号 |

（号码按 3-4-4 分段写便于核对位数；原图上是一串连续数字。全部为程序合成的假号。）

规则是一行正则（`entities.py::PHONE_RE`）：`(?:(?:\+86|0086)1[3-9]\d{9}|1[3-9]\d{9})`。
**放宽就会误报**——订单号（11 位首位 2–9）、快递单号（12–15 位）、日期流水号全都会命中，
dev 集专门放了 9 条这类负例来钉这条线。

但用户视角是"图上有号码，你没遮"。所以在「发现项」下方常驻一句话：

> 未框出**不代表安全**：位数不符、座机、订单号、境外号等都不在手机号规则范围内，
> 不会被自动遮盖。确实需要处理的，用「手动补框」。

措辞刻意选"不代表安全"而不是"判定为不敏感"——**规则管不到 ≠ 它不隐私**。
境外手机号（`+1 202-555-0143`）就是最典型的例子：它是真号，规则根本不认。

### 4.7 一些刻意的细节

- 号码一律**掩码显示**（`177****4805`），界面上不出现完整号码；
- 元数据单独一行说明"另有 N 条拍摄信息，不出现在清单里——它们始终整图清除"；
- 顶栏三个状态灯：本地运行 / 引擎就绪 / ExifTool 就位，出问题一眼定位；
- 处理耗时按阶段拆开显示（`text 3529ms  qr 137ms  face 22ms`），方便判断瓶颈。

## 六、成果与验证

### 6.1 工程指标

| 项 | 数值 |
|---|---|
| 自动化测试 | **223 条**全绿（契约 79 / 数据 39 / 界面 48 / 评测 49 / 运维 8） |
| 进度审计 | **40/40**（对照规格卡逐条检查） |
| 契约校验 | 所有真值与交接包都能过 JSON Schema v4 |
| 便携包 | 6,191 文件 / 474 MB / 自检 15 项全绿 |

### 6.2 检测效果（同一引擎，两种数据）

| 数据 | 手机号 | 身份证 | 二维码 | 误报 |
|---|---|---|---|---|
| 合成集（52 个对象） | 100% | 100% | 100% | 0 |
| **实拍 14 张**（屏幕翻拍 + 手写） | **84.6%**（11/13） | **66.7%**（2/3） | **0%**（0/5） | **0** |

**这两行必须一起讲**。只讲第一行是吹牛，只讲第二行是不公平——
合成图没有拍摄角度、没有反光、字太清楚，实拍掉下来是必然的。

二维码 0/5 的原因查清楚了：屏幕翻拍的**摩尔纹**把模块边界糊掉，
`cv2` 能定位到四个角，但解不出内容，透视矫正 + 二值化也救不回来。
**不是算法没写，是这种输入本身不可解**——所以报告里只能写"屏幕翻拍场景不可解"，
不能写"二维码检出不可用"。

### 6.3 三人协作的产物

| 角色 | 贡献 | 在本项目里的位置 |
|---|---|---|
| A | 检测引擎（OCR / 二维码 / 人脸） | `app/vendor/photocheck/detectors/a_engine/` |
| B | 载入 / 处置 / 复检 / 导出 | `app/vendor/photocheck/core/` |
| C（我） | 契约、数据集、评测、界面、审计、集成打包 | 其余全部 |

**这个项目本身就是"接口设计"的练习**：三个人代码风格不同，
靠一份 JSON Schema + 一套校验器把它们钉在一起，任何一方字段写错都会当场报错而不是悄悄跑偏。

## 七、局限与风险（主动说，比被问出来好）

| 局限 | 现状 | 影响 |
|---|---|---|
| 不训练模型 | 全用预训练模型 + 规则 | **这不是"训练模型"类项目**，别把它包装成 AI 训练 |
| 合成数据占比高 | 43 张合成 vs 14 张实拍 | 合成集 100% 不能当泛化能力 |
| 手写体误读 | 末几位会读错，掩码跟着错 | 已在报告里标为最高优先级问题 |
| 人脸无样本 | 有检测能力但没验过 | 只能说"支持"，不能说"验证过" |
| 二维码在屏幕翻拍下不可解 | 0/5 | 纸张实拍还没测；**解不出的码不会被自动遮盖**，界面会明确提示，需手动补框 |
| 只做静态图 | 不含视频、不含批量 | 单张交互式工具 |

## 八、可能的追问与回答要点

| 问题 | 回答要点 |
|---|---|
| 为什么不用大模型？ | ①离线要求；②隐私数据不该出本机，这是产品底线；③号码/证件是可判定的硬规则，用大模型反而不可解释、还会编 |
| 准确率多少？ | 分两行答：合成集 100%，实拍手机号 84.6%、身份证 66.7%、误报 0。并说明样本量小（n=13） |
| 怎么保证擦干净了？ | 擦完把每块区域**单独再读一遍**（OCR / 二维码），再做整图重扫；元数据用 ExifTool 独立复核 |
| 漏检怎么办？ | 三个兜底：手动补框、复检会报"计划外残留"、报告只写"本次未发现"不写"安全" |
| 最难的部分？ | 不是检测，是**让三个人对同一个字段理解一致**——最后靠 JSON Schema + 校验器解决 |
| 为什么不用 Gradio？ | 体积（197 MB）与定制受限；改成原生 HTML 后界面能按产品需要做，包也小了 |
| 如果继续做？ | ①补纸面实拍的二维码；②手写体加置信度标记；③批量处理与视频 |
