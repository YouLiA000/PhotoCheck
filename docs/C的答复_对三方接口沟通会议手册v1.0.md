**这份手册作为会议流程，我认，可以直接用。作为技术附件，第五部分必须整节替换。**

## 二、致命问题：§五 是另一份契约

### 2.1 逐条对照

| 项 | 手册 §五 草案 | 规格卡 §0.2（已冻结） | 后果 |
|---|---|---|---|
| 版本字段 | `schema_version: "v4"` | `contract_version: "photocheck/v4"` | 校验器直接判 `const_mismatch` |
| `kind` 枚举 | `text / qrcode / face / metadata` | `meta / text / qr / face` | **字符串对不上**，subtype 匹配与统计全落空 |
| `subtype` 枚举 | 含 `name / address / link / qrcode_url / qrcode_pay …` | `phone / idcard`；qr 用 `qr_wechat_pay` 等 11 项 | K-04 已把姓名、地址后置，首版不做 |
| 风险字段 | **无** | `risk: 1 / 2 / 3`（必填） | K-10 分级、K-12 面板无输入 |
| 置信度 | `confidence` | `detector_score` | 字段名不同；语义一致，可改名解决 |
| `evidence` | 对象 `{source, matched_rule, masked_value, raw_value}` | **字符串枚举** `exif / ocr_rule / qr_payload / face_box` | 结构不同；K-10 要求 evidence 单列展示 |
| 掩码值位置 | `evidence.masked_value` | `details.masked_preview` | 位置不同 |
| `raw_value` | `恒为 null`（保留该字段） | **禁止该字段存在**（泄漏红线黑名单） | 保留空字段会被判 `forbidden_key` |
| Decision | `{decision_id, det_id, action, method, source, plan_revision}` | `{finding_id, action, revision}` | method 属 plan item；revision 独立 |
| RedactionPlan | `{plan_id, plan_revision, strip_metadata, items[{det_id, bbox, method, color}]}` | `{image_id, revision, items[{id, finding_id, bbox, method}]}` | 多 strip_metadata/color；`det_id` → `finding_id` |
| VerificationReport | `overall` + 三态 `pass/partial/fail` | `disposal_state` **四态** + `checks[]` + `residuals[]` | **状态机不同**，见 2.2 |
| 主键粒度 | 一条记录装一个 `detections[]` 数组 | 一条记录 = 一个 Detection（扁平） | 我按扁平实现；包装格式要另写适配层 |

### 2.2 三处结构性差异，改名救不回来

**（1）VerificationReport 三态 vs 四态 —— 最危险**

手册是 `pass / partial / fail` + `overall`。规格卡是 `not_applicable / pending / passed / failed`。
少的两态恰好是真实会遇到的：

- `not_applicable`：用户全部选保留，没有待处理区域。三态里只能错填成 pass，等于谎报复检通过。
- `pending`：用户改了某个决定、`revision` 递增、复检还没重跑。三态里没有"未跑"这个状态，
  面板只能显示旧结果——这正是规格卡 §0.2 那句「旧验证报告立即失效并显示 pending」要防的事。

K-09 的增量排期（EXIF W2 / OCR W4 / QR W5 / 人脸 W6–W8）也是按四态设计的：前三次增量期间
人脸项就是 `not_applicable`。三态跑不通这个排期。

**（2）`kind` 用 `metadata` / `qrcode` 而不是 `meta` / `qr`**

看起来是命名口味，实际上是**统计维度**：我的评测表按 `subtype` 分组，subtype 的父级就是
kind。字符串一旦不一致，A 的输出在我这边全部落到"未知类别"，Recall / Precision 会集体变 0。
这种错误在联调时才暴露，而且看起来像"评测脚本写错了"，排查要半天。

**（3）Decision 里塞了 `method` 和 `plan_revision`**

规格卡的 Decision 只有 `finding_id / action / revision`。`method` 属于 `RedactionPlan.items`——
因为同一个对象可能先模糊后改纯色，那是**计划变更**，不是**用户决定变更**。两者混在一个
revision 上，B 就没法判断"是重画计划还是重跑复检"。

### 2.3 草案里有三样东西值得吸收（但要走变更流程）

不是全盘否定。以下三条规格卡没有，但确实有用：

| 字段 | 价值 | 建议 |
|---|---|---|
| `sha256` | 数据可追溯，lock 集封存本来就要求哈希 | 放 `manifest.csv` 或独立 `hash.json`，不必进契约记录 |
| `strip_metadata` | 显式表达"这版要不要清元数据" | 规格卡是整图自动清除、不询问用户，保留语义即可，不必成为字段 |
| `color` | 遮盖色可配 | 首版固定黑色即可；要进契约走 v4.1，三人同意后升版本号 |

**姿势建议**：会前另起一份 v4.0 草案，等于把已冻结的版本推倒重来。正确做法是
"以规格卡 §0.2 为 v4.0 基线，把这三条记为 v4.1 候选"，会上只决定要不要排进 v4.1。

## 四、我必须提前说清的一个立场：不同意 `idcard_invalid`

手册 A9 的建议默认值是「检出，`subtype=idcard_invalid`」。这条与规格卡 K-04 的 v1.3 修正
直接冲突，而且冲突的方向是错的。

K-04 原文（v1.3 修正）：

> 改为三态：校验不通过仍提示，但降为 risk 2 并标注「格式像身份证，校验位未通过（可能录错）」。

也就是说，校验位不通过这件事**已经由 `details.idcard_check = "fail"` + `risk = 2` 表达了**。
再加一个 `subtype=idcard_invalid`，等于用两个字段说同一件事，而且会让：

- subtype 统计多出一个"不是真实类别"的桶（它不是另一种对象，是同一种对象的另一种状态）；
- 与 `idcard` 的 Recall 被拆成两行，样本本来就少，拆完 n 都不到 5，只能标"仅作开发参考"；
- K-04 验收标准里那条"篡改一位的样本 → 不得标 pass，但必须保留为 fail（risk 2）"没法执行。

**我的处理**：数据集里已经按三态标了（`pass` 8 条、`fail` 1 条），风险规则我实现成了
`idcard_check=="pass" ? 3 : 2`。如果 A 认为三态不好做，可以会上提，但那需要改**规格卡**，
不是改手册——改规格卡要三人同意 + 升版本号，这是 §6 变更纪律写着的。

## 五、排期上有一处会当场卡住：A 的 W4 承诺超前了

手册 §七 写「W4：A 出 phone / idcard / qrcode 三类检测可用」。对照规格卡：

| 卡 | 负责人 | 规格卡周次 |
|---|---|---|
| K-03 OCR | A | W2–W4 |
| K-04 手机号 / 身份证 | A | **W4 末–W5** |
| K-05 二维码 | A | **W4–W5** |

也就是说，W4 结束时 A 能交的是 **K-03 完成 + K-04 首版**，二维码落在 W5。手册把三类压在
W4，A 要么做不到，要么赶工出个 demo 版——后者更糟，因为我会拿它跑基线表。

**建议改成**：

- W4 验收物：`K-03 + 手机号检测`（身份证允许 W5 补），二维码不要求；
- W5 验收物：`K-04 完整（含三态）+ K-05 二维码`；
- 我在 W4 用 fixtures 里的 mock Detection 顶住 eval.py 和界面，不让链路空转——这条手册
  §七 第 256 行自己也写了，我只是把它提前到 W4 就执行。
