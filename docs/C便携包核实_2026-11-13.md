## 结论

便携包能够启动并通过应用自检，主要检测链路可用。但不能原样发布，存在必须修复
的打包和隐私问题。

## 阻断问题

### 1. 包内带有上传副本和处理产物

包内 `work/` 共 23 个文件、约 2.87 MB，包括：

- 3 个上传图片副本；
- 3 个 `.name` 原始文件名记录，原文件名显示为微信图片和屏幕截图；
- 17 个已处理图片副本。

即使这些是测试素材，也不应进入分发包。发布包必须只含空运行目录或不含
`work/`，由应用首次运行时创建。

### 2. 夹带 Python 字节码缓存

包内有 872 个 `.pyc`，合计约 18.9 MB，并包含大量 `__pycache__`。这会：

- 增大包体；
- 固化构建机的源码状态；
- 在替换源码后增加旧字节码混入的风险。

便携包应排除 `__pycache__`、`.pyc`、`.pyo` 和 `.pytest_cache`。

### 3. 内置解释器启动报错

每次执行内置 Python 时均出现：

```text
distutils-precedence.pth
ModuleNotFoundError: No module named '_distutils_hack'
```

自检最终仍返回 0，但这是不完整裁剪造成的噪声和潜在兼容隐患。构建时应保留
`_distutils_hack`，或者同时移除对应 `.pth`，不能只删一边。

### 4. 缺少功能规格卡

压缩包只带 `项目说明.md`，没有 `docs/功能规格卡_v1.4.md`。这违反团队此前确定的
“发布包不得丢失功能规格卡”要求。

### 5. 源码和文档数字落后

- 项目说明写 6,236 文件 / 487 MB；实际源目录约 7,077 文件 / 518 MB。
- 包内应用源码比当前 B 集成版本旧，缺少多任务快照、上传内容验证和部分防护测试。
- `使用说明.txt` 存在 `D:////` 等格式错误。
- “证明擦干净了”属于过度表述，应改为“复检当前计划区域和最终导出文件”。

## 高斯模糊核实

原实现：

```text
kernel = 短边 / 4（取奇数）
```

在包内 3 张示例上实测：

| 样本 | 可决定文字区域 | 模糊后复检 |
|---|---:|---|
| demo-01 | 3 | 3 个残留，`failed` |
| demo-03 | 2 | 1 个残留，`failed` |
| demo-05 | 2 | 2 个残留，`failed` |

短边 1/2 仍使 demo-03、demo-05 失败；提高到短边 3/4 后：

```text
demo-01  3/3 区域 passed
demo-03  2/2 区域 passed
demo-05  2/2 区域 passed
```

因此决定保留规格卡要求的 `blur` 能力，但把高斯核提高到短边的 3/4，并保留
逐区域复检。不能因为调大参数就取消复检；其他字体、手写和低质图片仍可能失败。

## 我方整合

- 不复制 C 包内旧 `work/`、上传文件和处理产物。
- 继续使用我方较新的 `app/service.py`，保留多分析快照和上传内容验证。
- `app/main.py` 启动进程级网络 guard，仅允许本地 HTTP 监听，不允许外部连接和 DNS。
- `tools/build_app.py` 只复制运行时，不带 `work/`、测试、缓存和字节码。
- 自动同步 `app/vendor/photocheck`，避免 vendored 引擎与主运行时漂移。
- 构建前自动运行应用测试。
- 构建后自动检查必需文件、禁止目录、内置解释器启动和端到端自检。
- ZIP 外生成 `.zip.sha256`。
- 便携包加入 `docs/功能规格卡_v1.4.md`、评测协议、标注指南和 R-03 记录。
