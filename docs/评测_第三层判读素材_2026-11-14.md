## 1. 素材是什么

38 张 dev 有效图的**整图前后对照**（左原图 / 右 App 真实导出图），
每张标了像素改动率、处置状态、遮盖处数、检出数、残留数。

与 C 侧第二层的实测**完全一致**：

| 项 | A 的 HTML | C 的 layer2 |
|---|---:|---:|
| 图数 | 38 | 38 |
| `passed` | 32 | 32 |
| `not_applicable` | 6 | 6 |
| 遮盖总处数 | 52 | 52 计划区域 |
| 残留 | 0 | 0 |

说明两边跑的是同一套东西，不是两份互不相干的数据。

## 2. 两种粒度，别混着用

| 素材 | 粒度 | 适合回答 | 不适合 |
|---|---|---|---|
| A 的 `index.html` | **38 张整图** | 有没有影响阅读、哪张图可疑 | 数不清一处遮盖具体盖了几个对象 |
| C 的 `results/layer3_sheet/` | **52 个区域裁图** | 某个区域是否超出对象、误遮几个 | 看整体版式（裁图只有局部） |

**建议流程（两阶段，省时间）**：

1. 先用 A 的 38 张整图过一遍，标记「可疑」；
2. 只对可疑的图，打开 C 的区域裁图，数清误遮对象数。

不建议 52 张逐张从头看——整图能排除掉的，不必再钻局部。

## 3. 判读表（38 行）

已生成：`docs/eval-reports/layer3_review_38.csv`

| 列 | 填什么 |
|---|---|
| `image_id` / `state` / `change_pct` / `redactions` / `detections` / `residuals` | 预填，不要改 |
| `affects_reading` | **0 或 1**：遮盖是否挡住了非敏感但需要阅读的内容 |
| `over_redacted` | **对象个数**（0..`redactions`）：这图有几处遮盖明显超出被遮对象 |
| `note` | 一句话说明；没有就留空 |

规则：

- 6 张 `not_applicable` 的 `redactions=0`，两列都填 **0**；
- `over_redacted` 不能超过该图 `redactions`，超了转换脚本会拒绝；
- **姓名、单位、邮箱、地址不被遮不是缺陷**（A 的检测范围只有五类），
  不要记成「欠遮」；
- 改动 <0.5% 一律记 none，那是 JPEG 重编码噪声，不是漏遮。

## 4. 转成 layer3 JSON

```bash
python tools/make_layer3_sheet.py --from-image-csv docs/eval-reports/layer3_review_38.csv \
    --layer2 results/layer2/layer2.json --out-json results/layer3.json
```

- 每一行都填了才生成；缺行退出码 1；
- 输出 `summary.images=38`、`regions_reviewed=52`（按遮盖处数合计）、
  `affects_reading` / `over_redacted` 由填入值汇总；
- 再跑 `eval --layer3 results/layer3.json`，EV-02 才会转绿。

## 5. 机审初筛（不是人工判读）

对改动 ≥10% 的 9 张（`014/015/016/017/024/028/029/030/042`）做了视觉抽查：

**全部是二维码 / 手机号的大块遮盖，没有连带盖住姓名、地址、邮箱、金额。**
高风险的高百分比来自二维码本身面积大，不是盖过头。

另外抽查了 `041`（登记表三行号码）与 `009`（聊天截图）：
遮盖都只落在号码 / 证件号上，标签与聊天文字保留。

**这只用于减少人眼工作量，不能当判读结果。** CSV 里的两列仍然留空，
需要判读人自己确认；A 的要求是**两名判读人各自独立填，不要看对方的**。
