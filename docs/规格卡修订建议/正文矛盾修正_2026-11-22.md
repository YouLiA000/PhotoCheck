# 规格卡 v1.4 正文两处自相矛盾：修订建议（C 侧，2026-11-22）

> 背景：S-3 / S-6 / K-09 / K-03 的口径已由 A、C 签字确认，代码与审计均已对齐
> （PR #2 合并后 `audit` = 42 PASS / 0 PARTIAL）。
> 但**规格卡正文没有同步**，且正文内部两处互相打架。
> 本文只列需要改的段落与替换文本。2026-11-22 已由 B 依据 A/C 已签的
> K-09 与 S-3 口径同步到正文，并将正文版本标记为 v1.4.1。

---

## 为什么现在要改

审计不读规格卡正文，所以这两处不影响 `42 PASS`；但：

1. **签字对象是正文**。正文与已签口径不一致，等于签的和写的是两件事。
2. **答辩会被追问**。评委会拿正文对照代码，两句话对不上就是硬伤。
3. **内部自相矛盾比"与代码不一致"更难解释**——同一份文档第 831 行说收款码是 3，第 910 行说是 2。

---

## 矛盾一：K-09 里 `not_run` 的落点

**正文现状**（两处）：

`docs/功能规格卡_v1.4.md:203`

```
| `disposal_state` | `not_applicable`：无待处理区域；`pending`：未复检或存在 not_run / not_applicable；…|
```

`docs/功能规格卡_v1.4.md:538`

```
not_run / not_applicable -> disposal_state = pending
```

**已签口径**（K-09 规则 4、5）：

| 情形 | check | 汇总 |
|---|---|---|
| 明确没有执行 | `not_run` | **`failed`** |
| 已执行但检测器/方法不可用 | `not_applicable` | `pending` |

**代码事实**：`contract/validate_records.py:497 _derive_disposal_state` 按已签口径实现；
`not_run` 落 `failed`，`not_applicable` 落 `pending`。

**建议替换**：

`:203` 整行改为

```
| `disposal_state` | `not_applicable`：无待处理区域；`pending`：存在已执行但探针不可用的区域（not_applicable）；`failed`：至少一个区域 not_run 或复检失败；`passed`：全部待处理区域通过 |
```

`:538` 改为

```
not_run        -> disposal_state = failed，写入 residuals(reason=verification_not_run)
not_applicable -> disposal_state = pending
```

**为什么这条重要**：`not_run → pending` 会把「根本没检查」算成「待检查」，
正是 K-09 规则 2 要防的「绿勾掩盖缺失」。正文写反了，等于给了绕过口子。

## 矛盾二：收款码的风险等级

**正文现状**（同一份文档，两处相反）：

`:831`（二维码类型表）

```
| wxp:// 或 qr.alipay.com | **收款 / 支付** | 收款码，可能关联实名 | 3 |
```

`:910`（严重程度打分）

```
身份证（校验通过）/ Wi-Fi 密码 / 精确 GPS = 3；手机号 / 收款码 / 校验位未通过的证件号 = 2；…
```

**已签口径**（S-3）：四个 subtype 固定 risk 3，含 `qr_wechat_pay` / `qr_alipay`。

**代码事实**：`contract/risk_rules.py:35,36` 均为 3；`image-lock-003/015` 保留定案前
历史 risk 2（只影响标注，不影响运行时计算）。

**建议替换**：

`:910` 改为

```
**严重程度打分**：身份证（校验通过）/ Wi-Fi 密码 / 精确 GPS / 收款码与群码（S-3 四类二维码）= 3；手机号 / 校验位未通过的证件号 = 2；人脸 / 普通链接 / 设备型号 = 1。
```

**为什么这条重要**：`910` 是"打分规则"的唯一定义处，实现方按它写代码就会把
收款码判成 2，与 `831` 和 S-3 冲突。留着一行错的，比缺一行更危险。
