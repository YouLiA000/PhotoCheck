## 2. 第 5 节"两个缺陷"的核对（关键）

A 说："你们抄进 `a_contract.py` 的那份契约带着两个已知缺陷"，并给了验证代码
`from photocheck.detectors.a_contract import Detection`。

**这个对象在 C 仓库里不存在。** C 仓库没有 `photocheck/` 目录、没有 `a_contract.py`、没有 `Detection` 类。
C 的契约是独立实现（`contract/masking.py` + `contract/validate_records.py` + `contract/schema/`），从没抄过 A 的契约文件。

逐条核对 A 列的两个缺陷：

### 缺陷 1：身份证掩码正则结尾写死 `\d{4}`，末位 X 被拒

C 的掩码生成 `contract/masking.py::mask_idcard` 用 `value[-IDCARD_TAIL:]`（即 `value[-4:]`）截尾，
对末位 X 的证件 `value[-4:]` 天然得到 `123X`，**本来就支持 X**。测试
`contract/tests/test_masking.py` 里的形状断言也显式允许 X：

```python
IDCARD_SHAPE = re.compile(r"^[0-9]{4}\*{10}[0-9Xx]{4}$")
```

→ 缺陷 1 在 C 侧不存在。

### 缺陷 2：长数字串规则删分隔符，把日期 `2024-06-01` 当未掩码

C 的校验 `contract/validate_records.py::scan_masked_preview` 是 **leak 检测**（反向）：
只检查 `phone` / `idcard` 的 `masked_preview` 里有没有残留完整明文，**根本不校验 `meta` 的格式**。
schema 对 `masked_preview` 的唯一硬约束是"必须含 `*`"（`pattern: "\\*"`），没有格式白名单。

→ 缺陷 2 在 C 侧也不存在——C 压根没有"删分隔符再判数字串"这条规则。

### 根因

两边策略不同，不是谁抄了谁：

| | A（`core/contract.py`） | C（`contract/`） |
|---|---|---|
| 校验方向 | 正向格式白名单（`fullmatch` 正则） | 反向 leak 检测（抓残留完整明文） |
| 掩码格式 | `_IDCARD_MASK` / `_PHONE_MASK` 全匹配 | schema 只要求含 `*`，格式由 `masking.py` 生成保证 |
| meta 处理 | 退化为"不得含 7 位连续数字" | 不校验 meta 格式 |

两套独立、互补、不冲突。A 第 5 节的修复对 A 自己的契约有效，但指控 C"带着缺陷"是把 A 侧的记忆安到了 C 头上。
