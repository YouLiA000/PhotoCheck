## 三、Decision revision —— 已改成全局版本

**你的判断是对的：混合 revision 会被 `validate_records` 直接拒。**

改动（`ui/decision.py::build_decisions`）：

```python
old_rev = max((int(p.get("revision") or 0) for p in prev.values()), default=0)
changed = set(targets) != set(prev) or any(
    prev.get(fid, {}).get("action") != action for fid, action in targets.items()
)
revision = 1 if not prev else (old_rev + 1 if changed else old_rev)
```

- 首次 → 全部 `revision=1`
- 相同输入 → 幂等，不变
- **任一 finding 变了 → 全部升到同一个新版本**
- finding 集合本身变了（增删）也算变化

**测试同步改**：原 `test_deselect_produces_retain_and_bumps_revision` 断言"没变的不该动 revision"，
现在改成 `..._globally`，并加了一条硬断言：

```python

                 "剩余所有 Decision 必须共享一个 revision")
```

## 四、补框不触发 revision —— **这条我没做，说明理由**

你说补框增减/改坐标也应该升版，因为会改变 RedactionPlan。

**语义上我同意**，但 C 这边没有落点，两个原因：

1. **C 的界面不产 `RedactionPlan`，也不产 `VerificationReport`**。计划由你的
   `build_redaction_plan` 构造，复检报告是你的 K-09 产出。C 只交两样东西：
   `decisions`（契约记录）+ `manual_boxes`（素材）。
2. **revision 在契约里挂在 Decision 上**，`manual_boxes` 没有版本字段。要给补框升版，
   只能在 Decision 上做手脚——但那等于用一个字段表达两件事，读的人会误解。

**我的建议**：你构造计划时，把"批次"理解成 `max(decisions.revision)` 就够——
因为 **C 每次导出都是全量快照**（当前所有 decisions + 当前所有 boxes），不是增量补丁。
用户改了补框再导出，你拿到的是新快照里的 boxes；`decisions.revision` 没变，
但 boxes 的坐标变了，你按新坐标构造即可。

**如果你坚持要一个显式的 "box epoch"**，唯一干净的做法是在契约里给 `manual_boxes`
加一个 `revision` 字段。那是 schema 变更，要三人同意，我不单方面加。

## 六、Windows UTF-8 编码 —— 已修

**根因**：`✓`（U+2713）、`✗`、`↔` 不在 GBK 字符集里，`print` 直接抛 `UnicodeEncodeError`。

**修法不是强制 UTF-8**（那会依赖终端支持），而是**换 ASCII**：

```
✓ → [OK]     ✗ → [FAIL]     ↔ → <->
```

**验证**：

```bash
PYTHONIOENCODING=gbk python eval/eval.py --set dev --perfect
# → [OK] 自测通过：完美预测下指标全为 1.0
# → exit=0          ← 原来这里是 1
```
