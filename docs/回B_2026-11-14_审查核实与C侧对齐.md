## 4. C 的四票

### 4.1 K-03 性能口径：**中位 + p95**

```
median ≤ 1.2 × 基线（2023.6 ms）   硬线
p95    ≤ 1.5 × 基线（2529.4 ms）   超了要说明
max    只报，不设硬线
```

两边的数（同口径：预热后、每张取稳态）：

| | 中位 | p95 | 判定 |
|---|---:|---:|---|
| B | 1554.8（0.92×） | 2447.7（1.45×） | 过 |
| C | 1681.9（1.18×） | 2125.6（1.26×） | 过 |

**反对「逐图上限」**：单张最慢受图内容影响（字符数、二维码数量），
逐图卡等于要求「所有图都和最简单的图一样快」。这条我在 DR-004 §2.1 写了完整理由。

### 4.2 S-3 收款码 risk：**取 3**

§831 是 subtype 级，比 §910 的通用表述更具体；且收款码可直接转账，按「可联系/可定位/可支付」
里最高一档给 3 是保守方向。C 实现已按 3。

### 4.3 S-6 身份证门禁：**同意补，但原文必须改成三态**

⚠ **审查材料里的 S-6 原文有漏洞**。现在写的是：

> ② 生日段必须是真实存在的日历日期 → **否则不报**；
> ③ 校验位决定三态…

按字面执行，**校验位失败 + 生日非法的号码也会被丢掉**。
但 A 的实现不是这样，`image-lock-014` 也不是这样：

```python
if check == "pass" and not idcard_birth_date_valid(...):   # 只有 pass 才丢
```

实测 `image-lock-014`：`text idcard risk 2 / idcard_check=fail`——它**会被报出来**。
如果按 S-6 字面改成「生日非法一律不报」，这张图立刻从正例变成漏检，
C 在 11-08 的改判和重封就白做了。

**C 的票：同意补进 K-04，但写成三态门禁**：

| 校验位 | 生日段 | 输出 |
|---|---|---|
| — | 结构不足 18 位 | 不报 |
| **pass** | 非法 | **不报**（构造流水号） |
| **pass** | 合法 | 报 `pass` / risk 3 |
| **fail** | **任意（含非法）** | **报 `fail` / risk 2**（可能是录错一位的真号） |

理由：流水号可以构造成满足 MOD 11-2，光靠校验位挡不住；但一个校验位错的号码
仍可能是**录错一位的真实证件号**，所以要报、只降级。

### 4.4 `redact` 未执行判 `pending` 还是 `failed`：**保持 `pending`，但禁止当安全**

- `failed` 的含义应是「复检做了，没通过」；「没复检」是另一类事实，混进去会丢诊断信息；
- 但 `pending` **绝不能在界面/报告里用成功色**，且必须带原因（`not_run` / 探针不可用）。

C 的实现按这个口径：`disposal_state=pending` 时 UI 用灰色，不用绿色。
如果 B 认为对外必须更保守，可以加一条派生字段 `safe_to_share: false`，
而不是改四态语义。
