# DR-002 ｜ 2026-11-02（2026-11-06 落数据） ｜ 契约方言统一：qr typed 字段与 orientation

**结论**：A 与 C 的契约方言分歧，**一律采用 A 的方案**，因为两处都能追到规格卡原文。
C 侧的契约层已于 2026-11-02 落地，数据层于 2026-11-06 落地。

## 分歧与裁定

| 分歧点 | A 的方案 | C 原状 | 追到规格卡哪一句 | 裁定 |
|---|---|---|---|---|
| 二维码摘要字段 | `safe_domain` / `safe_ssid` | `masked_summary: "qr/qr_link"` | K-06 要求界面**显示域名与 SSID**；通用摘要给不出 | 采用 A |
| `orientation` 取值 | 只认 `exif_transposed` | 数据写 `as_stored` | 规格卡示例值写的是 `exif_transposed` | 采用 A |

## 理由

1. **规格卡是唯一标准**。两处分歧都不是"谁的实现更方便"，而是规格卡已经写了答案，
   只是 C 早期按自己的理解写了另一套。这种情况不投票，直接回到原文。
2. **`masked_summary` 表达不了 K-06 的要求**。用户要判断"这个码扫了会去哪"，
   `qr/qr_link` 等于没说；`example.com` 才是可用信息。
3. **`orientation` 不一致是定时炸弹**。C 的合成图没有 EXIF orientation tag，
   两种写法像素坐标恰好一致，所以一直没暴露；一旦接入真实手机照片（带 tag），
   A 会按 EXIF 转置坐标而 C 的真值没转，IoU 会整体崩掉，看起来像检测器坏了。

## 为什么锁集不能重生成

`gen_samples.py` 的绘制逻辑没改，理论上重生成能得到同样的图（实测 23/23 一致）。
但"理论上"不能作为封存集的依据：lock 的封存意义就是"任何改动必定被发现"，
一旦重生成时环境（Pillow 版本、字体、QR 库）有差异，像素就会变，而肉眼看不出来。

所以 lock 的迁移方式是：**改 JSON 字段，图一个字节不动**。
`seal_lock.py verify` 仍是唯一判据。
