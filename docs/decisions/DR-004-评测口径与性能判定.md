## 二、待表决（不等它，但要标出来）

### 2.1 K-03 性能判据：median + p95，不设逐图上限

```
测量：进程预热 1 次 → 每张图先跑 1 次作废（换图开销不计）→ 第 2 次开始计时
判据：median ≤ 1.2 × 基线（2023.6 ms）    ← 硬线
      p95    ≤ 1.5 × 基线（2529.4 ms）    ← 超了要说明
      max    不设硬线，但必须报出来
```

实测（同口径）：

| | median | p95 | max |
|---|---:|---:|---:|
| B 的机器 | 1554.8（0.92×） | 2447.7（1.45×） | 2558.1 |
| C 的机器 | 1681.9（1.18×） | 2125.6（1.26×） | 2205.1 |

**为什么反对逐图上限**：单张最慢由图的复杂度决定（密集版面、多文字块），
逐图卡 2023.6 等于要求"所有图都和最简单的图一样快"。实测同一批数据，
逐图卡会让 55% 的图不达标，但其中绝大多数是正常的长尾，不是性能退化。

**为什么 max 不设硬线**：p95 已经管住长尾；max 单点波动 ±30%，设硬线等于运气测试。

### 2.2 lock 集的定位：**防回归闸门，不是泛化证据**

lock 只有 **16 个对象**（phone 5 / idcard 4 / qr 7）。即使跑出 16/16，
95% 置信区间下界也只有 **79%**——撑不起"泛化能力"的结论。

所以：
- W8 / W20 / 答辩前各跑一次，**看的是"改动有没有把它弄坏"**，不是"模型多准"；
- 报告里写 lock 的数字时必须同时写 `n=16`；
- **lock 封存后不得加样本**（不可逆），这一条比数字本身重要。

## 四、两次错误结论（写进 DR 的理由）

这不是自嘲，是防止半年后有人重新提同样的方案。

| 时间 | 谁 | 结论 | 错在哪 |
|---|---|---|---|
| 11-07 | C | `image-dev-001` OCR 5513 ms，是 W4 线 2.7 倍，**根因是 4.8 倍像素** | 那是**新进程第一次调用**（含模型加载）。稳态 1678 ms |
| 11-08 | A | 差异主因是**字符数**（估 C 的样本约 550 字符） | 实测中位 **64.5** 字符，最大 143。估高一个数量级 |
| 11-08 | C | 修正为冷启动，但用 `--repeat 1` 测全批 | **每张图第一次也有额外开销**（dev-009：3258 → 1448 → 1418），`repeat 1` 测的是"冷图" |

三次都错在**测法**，不是谁不认真。所以 §2.1 把测量步骤写成了可执行的三行。

## 六、没选的那条路，为什么不行

| 被否的方案 | 谁提的 | 为什么不行 |
|---|---|---|
| **按像素归一化 T_ocr**（`ms/MP`） | C 2026-11-07 | 有反例：0.56 MP 密集文字 5783 ms，1.75 MP 稀疏文字 2624 ms。归一化会把这两张**判反** |
| **逐图 T_ocr 上限** | 隐含在"W4 线"里 | 等于要求所有图一样快；把图的复杂度当成性能缺陷 |
| **参考集相对校准**（先测固定图再算比值） | A 2026-11-08 | 原理对，但代价大（每包多带 3–5 张图、协议要改）；而实测同图跨机器差异只有 28%（C 快于 A），基线偏保守、不会误伤。**先做"预热 + 中位 + 写条件"这三件成本更低的事** |
| **containment 作主判据** | A 2026-11-07 提议过 | 遮盖框本来就该比内容框大，IoU 惩罚的是正确行为——但**改主判据 = 协议变更**，且会让历史数字全部不可比。折中：主判据不动，报告加 containment 辅助列 |
| **把 `known_gap` 引进 `eval/`** | —（A 明确拒绝） | 评测器里留"把漏检标成已知"的口子，谁都能塞。A 的 `known_gap` 只在他自己的自测脚本里 |
