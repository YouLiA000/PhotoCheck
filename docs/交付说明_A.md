## 二、三条命令

```bash
# 1. 校验你的输出格式（不合格会直接说哪条哪个字段）
python contract/validate_records.py <你的预测.json>

# 2. 用你的检测器跑 dev 集（--kinds 排除 meta，meta 是 B 的活）
python eval/eval.py --set dev --pred-dir <你的预测目录> --kinds text,qr

# 3. 评测器自测（真值当预测，必须全 1.0；不过说明评测器坏了，不是你的问题）
python eval/eval.py --set dev --perfect
```

**预测文件格式**：每张图一个 JSON 数组，**文件名必须等于 `image_id`**：

```
preds/
  image-dev-001.json   ← 内容是 Detection[] 数组
  image-dev-002.json
```

文件名与 `image_id` 不一致时，评测**直接退出码 2**，不会给 0 分。0 分看起来像检测器完全失效，会把人带到错的方向。

## 三、你问的四件事

### 3.1 `+86` 样本：会造，且按你给的验收点验

| 形态 | 示例（掩码写） | C 会验什么 |
|---|---|---|
| 区号 + 空格 | `+86 138****8000` | 真值 bbox **从区号第一个字符起算** |
| `0086` + 短横 | `0086-139****9000` | 剥前缀后再掩码 → `139****9000`，不是 `0086****39000` |
| 紧邻 | `+86138****8000` | 剥前缀后仍按 11 位校验 |

**另外加两个负例**：前缀后少一位、前缀后多一位，确认不会把 13 位整体当号码。

### 3.2 IoU 要不要改 containment：先不改，但你的观察我记下了

**你说得对**：qr 真值含静区导致 IoU 上限 0.77、text 真值是 ink 框而 OCR 框自带外扩、4 个 idcard 压在 0.541~0.603。这是**系统性偏差，不是检测质量问题**。

**但不改**，三条理由：

1. **C 的 dev 集上你没被惩罚**：召回 100%（44/44）、精确 100%、误报 0。你 samples 上的偏差是 **samples 自己的真值口径**问题（真值含静区、ink 框），不是评测器的问题。
2. **改判据是评测协议变更**，要三人同意，写进 DR-003。我不能单方面改。
3. **containment 有它自己的漏洞**：它不惩罚"框得太大"。遮盖框大是对的，但无限大也能过 containment——那就变成了"全图涂黑也算通过"。

**如果你要推这个改动**，给我一份对比数据：同一批样本，IoU 0.5 与 containment 各自的通过/失败清单，以及差异项的原因分析。我拿数据去提表决，比空对空有说服力。

## 六、本包对应的提交

包内 `MANIFEST.sha256` 记录了每个文件的 SHA-256 与生成时的 git 提交。**验收时先跑一次校验**：

```bash
sha256sum -c MANIFEST.sha256
```

不匹配说明文件在传输中被改过，不要用。

> `sha256sum -c` 会先打印几行 `WARNING: … improperly formatted` —— 那是 MANIFEST 顶部的 `#` 说明行，**无害**。判断标准是看正文每一行是否 `…: OK`，只要没有 `FAILED` 就通过。
