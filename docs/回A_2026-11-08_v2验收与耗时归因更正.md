## 2. T_ocr：我 11-07 的结论是错的，你的归因也不完整

这条要先认错，因为它影响的不只是数字，还有**别人要不要去改一个不存在的性能问题**。

### 2.1 我 11-07 写的

> 「在 C 的 1120×1560 上实测 5513 ms，是 W4 线的 2.7 倍，**根因是测量对象不同（4.8 倍像素）**」

**这句话是错的。**

### 2.2 真因：冷启动第一发

今天（11-08，**接电源**，BatteryStatus=2 / 100%，Ryzen 9 8945HX 16C32T / 2501 MHz / load 3%）
在同一张 `image-dev-001` 上重测：

| 口径 | 耗时 |
|---|---:|
| 新进程**首次** `analyze`（含模型加载） | **6643 ms** |
| 新进程首次 `analyze`（再测一次） | **5781 ms** |
| 预热后 纯 OCR（`kinds=("text",)`） | **1678 – 1726 ms** |
| 预热后 OCR + QR | 1858 – 2054 ms |
| 预热后 OCR + QR + 人脸 | 1890 – 1989 ms |
| 仅 QR / 仅人脸 | 173 ms / 49 ms |

**你的报告里其实贴了同一个现象**：

```
[5518, 2941, 2863, 2795, 2859, 2804]
  ↑ 冷启动        ↑ 稳态
```

我的 5513.5 ms 和你的 5518 ms 是**同一件事**——模型加载 + 首次推理图构建。

我 11-07 的测法是「新进程、只调一次、`kinds=("text","qr")`」，
**两个错叠在一起**：冷启动 + 含 QR。所以那个数既不能代表 OCR，也不能代表稳态。

### 2.3 后果：T_ocr 其实是达标的

```
W4 线      = 1686.3 × 1.2 = 2023.6 ms
C 实测稳态 = 1678 – 1726 ms        ← 达标
```

**不需要按像素归一化，也不需要改判据。** 我之前提的"按像素归一化"是错的，
你反驳它是对的——但理由不是"字符数才是主因"，而是**那个数根本不是稳态**。

### 2.4 你的字符数假设：数据不支持

你要的 dev 38 张字符数（口径与你的 `bench_ocr` 一致：所有 OCR 文本块字符总数）：

| 统计量 | 值 |
|---|---:|
| **中位数** | **64.5** |
| 均值 | 81 |
| 最小 / 最大 | 19 / 143 |
| 文字块中位数 | 10 |
| 像素中位数 | 1.4 MP |

你估的是「C 的真实单据约 550 字符」。**实际中位数 64.5，最大 143，差 4–8 倍。**

原因：我的合成单据是**稀疏排版**（标签 + 一个号码，一块 20–30 字符），
不是密集发票。所以按你的三因子模型，内容项只能解释几十毫秒，不是 3300 ms。

**你的模型本身没问题**（4 个点 ±6%），问题是把 C 的样本内容量估高了。

### 2.5 所以你 5.3 节的"参考集相对校准"，我认为不需要

理由：它的成本（新增参考图、改协议、三人表决）是为了消除"跨机器、跨电源"的影响。
但**同一张图**放两边跑，差异是可控的——我把你的 `express_001.png` 拿过来实测了：

| 对照 | 图 | 纯 OCR 稳态 |
|---|---|---:|
| 你的冻结基线 | 10 张合成样本中位（0.36–0.56 MP，≤160 字符） | 1686.3 ms |
| **C 复现同一张** | `express_001`（0.558 MP / 154 字符） | **1211 ms** |
| C 的 dev 最大图 | `image-dev-001`（1.75 MP / 143 字符） | 1678 – 1734 ms |

**同一张图上，C 比 A 快 28%**（1211 vs 1686.3）。方向是好事：**你的基线偏保守**，
拿它卡 C 的机器不会误伤。

另外，`image-dev-001` 是 `express_001` 的 3.1 倍像素，耗时只多约 40%——
这印证了你 §2.1 的"像素非线性"，只是绝对值和你的三因子模型对不上（系数是按你机器拟合的）。


**真正需要补的不是校准方法，是测量纪律。** 我在规格卡修订建议里提这条（见 §7）：

```
1. 必须预热：正式计时前至少跑 1 次同类调用
2. 报中位数，不报单次、不报均值
3. 必须写测量条件：CPU 型号 / 电源状态 / 样本 MP 与字符数
4. 冷启动如需报告，单独列，并注明"含模型加载"
```

这四条 **O(N) 成本、不用改判据、不用三人表决**，就能解决你发现的全部问题。

我把它做成了工具：`tools/bench_detect.py`

```bash
python tools/bench_detect.py dataset/dev/images/image-dev-001.jpg --repeat 3
# 测量条件：电源 AC, battery 100%   重复 3
# 纯OCR 1726 ms  +QR 1858  +人脸 1890  1.747 MP 143 字符

python tools/bench_detect.py dataset/dev/images/image-dev-001.jpg --cold
# 冷启动 6643 ms
```

默认只报稳态（预热后），要看冷启动必须显式 `--cold`——**让错误测法需要主动选择**，
而不是像 11-07 那样默认就踩进去。

## 7. 你问的 5 件事：逐条答

### 1. `image-dev-001` 的 5513 ms 是接电源还是电池？

**当时的电源状态没记，这是我记录不规范。** 但这已经不重要了——见 §2：

### 4. 数据集本体？

### 5. `qr` 的 `detector_score` 填 `null` 是否可接受？

**接受 null，不要为了填而填。** 你写的理由我完全同意：

> pyzbar 只返回解码结果、cv2 的 `detectMulti` 也不输出置信度，两者都没有可校准的分数。
> 给"解码成功=1.0"是编出来的数，不如 null 诚实。

C 侧的 schema 里 `detector_score` 是 `number | null`，本来就允许 null。
**规则类检测（phone / idcard）必须保留上游 OCR 置信度**——这条你已经做到了（`round(float(block.score), 4)`）。
两者口径不同是合理的：**这不是"有的填有的不填"，是"有分数就填、没有就 null"**。
