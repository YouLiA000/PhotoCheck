## 3. 误报 1：`qr_unknown` 框住了纯文字区（7 条）

### 证据

| image_id | bbox | 长宽比 | 框里实际是什么 |
|---|---|---|---|
| image-dev-001 | [310, 209, 200, 342] | 0.58 | 快递单地址栏，纯文字 |
| image-dev-004 | [312, 526, 210, 356] | 0.59 | 地址 + 身份证号 + 品名，纯文字 |
| image-dev-009 | [327, 193, 395, 544] | 0.73 | 聊天记录竖排文字 |
| image-dev-012 | [120, 44, 627, 348] | 1.80 | 顶部标题区，纯文字 |
| image-dev-018 | [235, 112, 624, 493] | 1.27 | 正文段落 |
| image-dev-021 | [307, 208, 166, 263] | 0.63 | 地址栏 |
| image-dev-031 | [305, 209, 356, 426] | 0.84 | 地址栏 |

我逐张裁图看过：**这 7 个框里一个二维码都没有**，全是文字。

### 根因判断

你的 `detect_qr()` 在解不出码时仍保留框（`decodable=False` → `qr_unknown`）。
问题在于**候选框的来源**：pyzbar / `QRCodeDetector` 在文字密集区会产生误候选，而
"解不出也保留"这条策略没有对候选做几何约束，于是整块文字区被当成一个码。

### 建议（按性价比排序）

1. **长宽比 + 面积双重约束**：二维码是正方形，实测这 7 条的长宽比落在 0.58~1.80。
   建议 `qr_unknown` 只保留 `0.75 ≤ w/h ≤ 1.35` 且 `min(w,h) ≥ 40px` 的框。
   这条能挡掉 5/7（0.58、0.59、0.63、0.73、1.80），代价接近零。
2. **要求定位符证据**：只保留检出 ≥2 个 finder pattern（三个角上的回字方块）的候选。
   这条能挡掉全部 7 条，但要改检测逻辑。
3. **兜底方案**：`qr_unknown` 不产出 Detection，只在 `warnings` 里记一行。
   代价是漏掉"图里确有码但解不出"的情况——不过那种情况用户也拿不到内容，
   保留一个框的实际价值本来就低。

我倾向 **1 + 3 组合**：先按几何过滤，剩下仍解不出的降级为 warning。

## 4. 误报 2：身份证没校验出生日期段（1 条）

### 证据

| image_id | bbox | 框里的内容 | C 的真值 |
|---|---|---|---|
| image-dev-031 | [306, 440, 361, 33] | 18 位数字，**生日段为 2026-13-32**（13 月 32 日） | **负例**（`verdict=negative`） |

这串数字的生日段是 **2026 年 13 月 32 日**——不存在的日期。它是我们故意造的"流水号"，
用来测"形似但不是"的识别能力。（完整号码不在文档里落明文，看 `dataset/dev/negatives.json`
或直接看 `image-dev-031` 的 bbox 区域。）`negatives.json` 里有明确登记：

```json
"image-dev-031": [{"bbox": [303, 441, 366, 32],
  "note": "18 位但生日段非法（13 月 32 日），是流水号不是证号"}]
```

### 根因

你现在的身份证规则是 **18 位 + MOD 11-2 校验位**。这串号码位数对、校验位恰好也对，
所以被判成 `idcard`。缺的是**出生日期段合法性**校验：

```python
# 第 7-14 位 YYYYMMDD
year, month, day = int(s[6:10]), int(s[10:12]), int(s[12:14])
valid_date = 1900 <= year <= 2099 and 1 <= month <= 12 and 1 <= day <= 31
# 严格一点可以查当月天数与闰年
```

### 建议

加上日期段校验，**但不要因此丢弃整条 Detection**。按 K-04 三态：

| 情况 | 应产出 |
|---|---|
| 18 位 + 校验位过 + 日期合法 | `idcard_check=pass`，risk 3 |
| 18 位 + 校验位过 + **日期非法** | 不报（这是流水号） |
| 18 位 + 校验位不过 | `idcard_check=fail`，risk 2（**不是负例**） |

第 3 条务必别写反——我们之前踩过，会把 Precision 直接污染。

## 6. 需要你确认：两套评测器的口径不同

你新加的 `core/eval.py` 是一套独立实现，README 里写"须与 C 的 eval.py 对齐"，

## 11. 更正：第 8 条不是你的 bug，是我们标错了（2026-11-07 00:25）

你最新的包（含 BC-0009 / BC-0010）我复测了。**7 条 `qr_unknown` 全部消失，精确率从 84.6% 升到 97.8%。**

### 事实

那条号码（`1101**********4644`）同时有两个问题：

| 判据 | 结果 |
|---|---|
| 18 位 | ✅ |
| **校验位** | ❌ 前 17 位加权和 mod 11 = 10，应得校验位 `2`，实际是 `4` |
| 生日段 | ❌ 2026-13-32 |

你判成 `idcard_check=fail` + `risk 2`，**完全符合规格卡 K-04**：

> v1.3 修正：……改为三态：校验不通过仍提示，但降为 risk 2
> 验收：篡改一位的样本 → **不得标 pass**，但必须保留为 `idcard_check = fail`（risk 2）

而我们把它登记在 `negatives.json` 里当"不该报的负例"——**违反了自己引用的这条**。

### 根因

我们的生成器把两个错误叠在同一个样本上：

```python
# 旧代码：末位随手填
"fake_id": lambda r: "110101" + "20261332" + f"{r.randint(100, 999)}" + r.choice("0123456789"),
```

设计意图是"造一个生日段非法的流水号"，但末位随机导致 **约 10/11 的样本校验位也不通过**。
于是它既不是"有效身份证"，也不是"该被丢弃的流水号"，而是一条 fail 正例。

### 已改

```python
# 新代码：校验位算对，只让日期非法
"fake_id": lambda r: (lambda body: body + id_checksum(body))(
    "110101" + "20261332" + f"{r.randint(100, 999)}"
),
```

重生成后 dev-031 的号码校验位通过、生日段仍是 20261332。你的 BC-0010 逻辑正确丢弃了它。
