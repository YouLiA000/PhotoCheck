## 一、标的是什么

只标**位置或字段明确、能自动检测、处理完能再验证**的个人信息线索。首版三类：

| kind | 具体对象 | 标不标框 |
|---|---|---|
| `meta` | EXIF 里的 GPS、拍摄时间、设备型号 | **不框**（元数据没有像素位置） |
| `text` | 手机号、身份证号 | 框 |
| `qr` | 联系人 / 名片 / 支付 / Wi-Fi 类二维码 | 框 |

不标的：人脸、地址门牌、快递单号、学号、条形码、车牌、银行卡、普通链接二维码。
**这条不是懒，是边界。** 判据在规格卡的"隐私总定义"一节，越界标注会直接污染评测结论。

## 四、每一列什么意思

**前 9 列是《功能规格卡 v1.4》K-13「标注字段」表定义的，一个字都不改。**
后面几列是 C 为了把真值喂进契约 v4 加的扩展列，不进契约记录。

| 段 | 列 | 必填 | 取值 | 说明 |
|---|---|---|---|---|
| 规格卡 | `file` | 是 | `images/image-dev-001.jpg` | 相对 `dataset/<set>/` 的路径 |
| 规格卡 | `set` | 是 | `dev` / `lock` | 由 `scene_id` 推导，不手填（见 §5.7） |
| 规格卡 | `scene_id` | 是 | `scene-receipt` 等 | 绑定模板；同场景只能整体进 dev 或整体进 lock |
| 规格卡 | `kind` | positive 必填 | `meta` / `text` / `qr` | 留空即表示该行是负样本 |
| 规格卡 | `subtype` | positive 必填 | 见文末 | 留空即表示该行是负样本 |
| 规格卡 | `bbox` | 除 meta 外必填 | `520,410,220,42` | `x,y,w,h` 逗号分隔，左上角原点，含 2~3px 余量 |
| 规格卡 | `should_hide` | 否 | `0` / `1` | **策略标签**，不是用户选择。positive/meta 记 1，negative 记 0 |
| 规格卡 | `difficulty` | 是 | `easy` / `hard` | 小字、旋转、模糊、低分辨率、部分遮挡、多目标 |
| 规格卡 | `note` | 否 | 文本 | 判断理由。**不得贴号码或二维码原文** |
| 扩展 | `verdict` | 否 | `positive` / `negative` | 规格卡没有这列。写上更明确；留空时按 kind 是否为空判断 |
| 扩展 | `det_id` | 否 | `det-<image>-<kind>-<n>` | 人工留空即可，导入时自动编号 |
| 扩展 | `masked_preview` | text 必填 | 含 `*` 的掩码 | 如 `138****0000`。**禁止写明文** |
| 扩展 | `idcard_check` | 身份证必填 | `pass` / `fail` / `na` | 校验位正确=pass，格式像但校验不过=fail |
| 扩展 | `decodable` | qr 必填 | `0` / `1` | 该二维码当前能否解出 |
| 流程 | `annotator` | 否 | 姓名 | 谁标的 |
| 流程 | `checked` | 否 | `0` / `1` | 是否已复核 |

**注意 `risk` 不在标注字段里。** 规格卡 K-13 只把 `should_hide` 列为策略标签；`risk`
是契约 `Detection.risk` 的必填值，由 `contract/risk_rules.py` 按 K-04 / K-10 的规则算出。
标注者不判风险——否则同一条 Finding 在 A 的检测器和我这边会有两个分值，联调时说不清。

**`should_hide` 和 `Decision` 的区别**：前者是「按规范该不该遮」（标注侧、固定值），
后者是「用户实际选了什么」（交互侧、可随时改）。混在一起就分不清「该遮没遮」和
「用户主动保留」——评测里这是两种完全不同的结论。

`subtype` 取值：`gps` `datetime` `device` `serial` `thumbnail` `software`（meta）；
`phone` `idcard`（text）；`qr_wechat_card` `qr_wechat_group` `qr_wechat_pay` `qr_alipay`
`qr_wifi` `qr_vcard` `qr_contact` `qr_geo` `qr_code` `qr_link` `qr_unknown`（qr）.

## 五、判断口径（会分歧的就是这些）

### 1. 手机号：先归一化，再判 `1[3-9]\d{9}`

- 写成 `138 0013 8000`、`138-0013-8000` 的**算手机号**，框整段（含分隔符）。
- 11 位纯数字但首位是 2–9 的，**不是**手机号 → 负例。
- 首位 1、第二位是 0/1/2 的，**不是**有效号段 → 负例。
- 前后紧邻其他数字（如 13 位串里的 11 位）→ 不单独算，避免把工号切出号码。

### 2. 身份证：校验位不通过仍然是正向

18 位、前 17 位数字 + 末位数字或 X。

- 校验位对 → `idcard_check=pass`，`risk=3`
- 校验位错 → `idcard_check=fail`，`risk=2`（**不是负例**，系统确实"检出了身份证"）
- 不是 18 位身份证形态 → 不标

> 这一条最容易被标反。规格卡 K-04 的 fail 态存在的意义就是"格式像但校验不过"，
> 它属于检出结果，不属于误报。

### 3. 二维码：只记"能不能解"和"哪一类"，内容一个字都不进表

- `decodable=1` 且解出名片 → `qr_vcard`
- `decodable=1` 且解出 Wi-Fi → `qr_wifi`
- 解不出（已损坏/被裁）→ `decodable=0` + `qr_unknown`
- **`note` 里也不许写解出来的内容**，包括 Wi-Fi 密码、姓名电话。要写就写类别。

### 4. 元数据：不画框

meta 行的 `x/y/w/h` 留空。`masked_preview` 可写"GPS 坐标"这类说明，**不写真实经纬度或时间**。
一张图有 GPS + 时间 + 机型就写三行，不要合成一行。

### 5. 一段文字里混了多种信息

只框目标号码本身，不框整行。例如"张三 138xxxxxxxx 北京市…"，只框手机号那一段。

---

### 6. 边界判定五条（不许现场商量）

补充清单 §3.4 列了五种歧义，这里一次写死。**改这些等同改接口，要三人同意。**

| 情况 | 判法 | 理由 |
|---|---|---|
| 18 位、校验位不通过 | positive + `idcard_check=fail` + risk 2 | 规格卡 K-04 三态就是为此存在；不新增 `idcard_invalid` 枚举（改枚举要三人签字，且会污染 subtype 统计口径） |
| 11 位但号段不合法（首位 2–9，或 1 后第二位 0/1/2） | negative | 它确实是"像手机号但不是"的典型误报来源，必须进 negatives 才能算误报率 |
| 运单号 / 订单号（长度接近 11） | negative + note 写明"运单号" | 同上是干扰项；不标就永远不知道正则有没有放宽 |
| 带 `+86`、空格、连字符 | positive，**bbox 含整个前缀** | 归一化后再判 `1[3-9]\d{9}`；框住整段是因为遮盖要盖全，漏掉 +86 等于没遮 |
| 二维码解不出 payload | positive + `decodable=0` + `qr_unknown` | 检测到了就该遮（解不出也可能是拍糊），但必须记下"解不出"这一事实 |

**对 A 的约束**：这五条同时是 A 的规则实现口径。A 的正则必须先归一化再匹配，且对
"11 位但号段不合法"必须不报。两边不一致时，以本表为准，改表不改代码。

### 7. scene_id 绑定模板（防数据泄漏）

- `scene_id` 由模板决定（`scene-receipt` / `scene-chat` / `scene-card` / `scene-notice`）。
- **同一 scene 的全部样本只能整体进 dev 或整体进 lock**，不许对半切。理由：同模板的图
  长得几乎一样，切一半等于把答案漏给模型看。
- `set` 列由 scene 推导，标注时不手填。要扩 lock 集就**新造模板**，不是从 dev 里挑。

## 八、一致性验收怎么做

1. 两人**各自独立**标同样的 5 张（覆盖单据 / 聊天 / 名片 / 表单各一张，且含至少 1 张负例图）。
2. 比对两件事：
   - `verdict` 逐行是否一致（这是硬指标，不一致就是口径没写清）；
   - 同一对象的 bbox 是否达 IoU ≥ 0.5 且 subtype 相同（规格卡主口径）。
3. 不一致的条目**逐条写进失败案例库**（`reports/failure_cases.md`），注明是"口径没写清"还是"标错了"。
   口径问题改本指南并升版本号，标错的问题升级复核流程。

### 匹配口径：主口径按规格卡，宽口径只作敏感性分析

规格卡 K-13「工具」表写死：**对象级匹配 = IoU ≥ 0.5 且 subtype 相同**。这是主口径，
所有主表都用它，不能换。

| 口径 | 用途 | 规则 |
|---|---|---|
| **主口径（规格卡）** | 三张评测表、结题报告 | IoU ≥ 0.5 且 subtype 相同，一个真值框只匹配一个预测框 |
| 敏感性分析（非规范） | 附录，回答「换个阈值结论还成立吗」 | 文本类放宽到 IoU ≥ 0.3 或（中心点落入真值框 且 高度重叠 ≥ 60%）；qr / face 仍用 0.5 |

文本行是细长条，OCR 的框常比字形框大一圈，卡 0.5 会偏严——这正说明为什么需要那一栏
敏感性分析。但**报告的主结论只认 0.5**，否则别人复现时对不上规格卡。

### 人工一致性：用 Cohen's kappa，不用原始一致率

S4 的双人判读（W18）同理。理由：30 个对象里若 28 个都是「完全不可读」，两人全判对，
原始一致率就有 93%，看着很好——但那主要是**数据本身太容易**，不是两人判得一致。
kappa 会扣掉「碰巧一致」的部分。

```python
def cohen_kappa(a: list[str], b: list[str]) -> float:
    n = len(a)
    agree = sum(1 for x, y in zip(a, b) if x == y) / n
    pe = sum(a.count(k) * b.count(k) for k in set(a) | set(b)) / (n * n)
    return 0.0 if pe == 1 else (agree - pe) / (1 - pe)
```

口径：κ ≥ 0.8 一致性强，0.6–0.8 可接受，**< 0.6 必须回去改量表**，不能直接出结论。

### 三级判读量表（S4 双人抽检用）

| 等级 | 定义 |
|---|---|
| A 完全不可读 | 一个字符都认不出 |
| B 部分可读 | 能认出 1–5 个字符，但拼不出完整号码 |
| C 完全可读 | 能认出 ≥ 6 个字符，或能拼出完整号码 |

**「读到几位算部分可读」必须写死**（这里定 1–5 位），否则一个按「能看出是 1 开头」判 B、
一个判 A，kappa 直接掉到不可用。

## 九、已知偏差（写报告时要交代）

1. **合成图没有拍摄角度**。全部轴对齐，没有透视与旋转。真实手机照片的倾斜会让 OCR 掉点，
   这条缺口只能靠后期补的授权真实照片填，**不能靠合成图假装**。
2. **文字过于清晰**。即使加了噪声与 JPEG 压缩（质量 62–88），识别难度仍低于真实翻拍。
   因此 dev 集上的检测指标**偏乐观**，报告里必须写这句。
3. **负例是"设计出来的"**，覆盖了 5 种典型形态，不代表自然分布。真实场景里还存在
   "多行断裂的号码""手写号码"等形态，暂未覆盖。
4. **人脸不在本数据集内**。K-07 已移出必做，人脸栏一律 `not_applicable`。
5. **只有合成样本，没有实拍**。补充清单 §3.2 要求保留 10–15 张真实拍摄的道具图，用来
   回应「全合成泛化性」的质疑；这批图要团队自己拍（内容虚构、拍摄条件真实）。
   合成与实拍的结果**必须分开报告**，不许混算平均值。

## 十、bbox 口径：每类具体框到哪（2026-11-07 补）

这一节是被 A 问出来的——他在自己 samples 上算 IoU 时发现 qr 上限只有 0.77，
才发现两边的框不是同一个东西。**以后不用猜了，就按这里。**

| kind | bbox 框什么 | 为什么这么定 | 实测影响 |
|---|---|---|---|
| **qr** | **码本体 + 静区**（`qrcode.QRCode(border=2)` 后整张图的边界） | 静区是解码的一部分。只盖码本体、留着静区，码可能仍可解；遮盖要盖到"这块不可用" | 检测器只框码本体时，IoU 上限约 0.77 |
| **text** | **`ImageDraw.textbbox` 的 ink 框**（字形实际占的矩形，不含行距） | 这是"文字在哪"的最紧定义 | OCR 框通常自带外扩，IoU 会偏低但不会低于 0.5 |
| **meta** | **`null`** | 元数据没有空间位置，契约强制 bbox 为 null | 不参与 IoU |
| **face** | 人脸区域外接矩形 | — | C 无人脸样本 |

**评测评什么、不评什么**：

- 主判据 **IoU 0.5**（`eval/config.py` 写死）
- 报告同时给 **containment**（GT 覆盖率 ≥0.9 且 GT 中心在框内）作辅助列
- **不因为 IoU 低就改判据**：遮盖框本来就该比内容框大，IoU 惩罚的是正确行为。
  但改判据是协议变更，要三人同意（见 `docs/回A_2026-11-07_判据与耗时基线.md` §1）

## 十一、subtype 枚举：哪些能评、哪些只能判（2026-11-07 补）

规格卡 `subtypeQrEnum` 有 **11 项**，但 C 只有 5 类真值。

| 有真值、可直接评 | 无真值、只能靠规则判 |
|---|---|
| `qr_link` / `qr_wifi` / `qr_vcard` / `qr_wechat_pay` / `qr_unknown` | `qr_alipay` / `qr_geo` / `qr_contact` / `qr_wechat_card` / `qr_wechat_group` / `qr_code` |

**不缩枚举**（2026-11-07 三方一致）：A 的规则链 11 个都会产出，删 `qr_alipay` 只是把支付宝码
从 risk 3 降成 `qr_link` / risk 1，是**信息损失不是简化**；`qr_code` 更不能删——pyzbar 恢复后
EAN13 要落这里。

**报告口径**：这 6 类**不出现在指标表里**，标注为"仅规则可判，无样本"。不许拿规则命中当"检出率"。

## 十二、负例写进 `negatives.json` 的原则（2026-11-07 补）

负例不是"随机塞一串数字"，它**必须写清楚依赖哪条规则不成立**。否则出了问题说不清
是标注错了还是实现错了。

| 负例类型 | 依赖的规则 | 写进 `note` 的话 |
|---|---|---|
| 11 位、首位 2-9 | 手机号首两位必须是 `13x`–`19x` | 「11 位纯数字但首位是 2-9，不是手机号」 |
| 19 位卡号 | 身份证长度必须是 18 | 「19 位银联卡号，长度不符」 |
| `2026-13-32` 的 18 位号 | **生日段必须是真实日期** | 「18 位但生日段非法（13 月 32 日），是流水号不是证号」 |
| 座机 `010-xxxxxxxx` | 手机号不带区号短横 | 「座机号，11 位手机号规则不应命中」 |

**重点说第三条**：这类负例**只靠校验位是挡不住的**——流水号可以构造成满足
MOD 11-2 的校验位。挡住它的是"生日段必须是一个真实日期"这条门禁。

**身份证三态（S-6 共识，2026-11-15）**：

| 18 位结构 | 校验位 | 生日段 | 标注 |
|---|---|---|---|
| 否 | — | — | 不报 |
| 是 | pass | 合法 | `Detection` / `idcard_check=pass` / risk 3 |
| 是 | **pass** | **非法** | **负例**（构造流水号；`image-dev-031` 即此类） |
| 是 | **fail** | **任意** | **正例** / `idcard_check=fail` / risk 2（`image-lock-014` 即此类） |

**只有「校验位 pass + 生日非法」才是负例。** 校验位 fail 时，生日再怪也要报——
它可能是录错一位或两位的真实证件号。被丢弃的 18 位候选仍占用字符区间，
不能被手机号规则从中间切成 11 位。

正式修订文本见 `docs/规格卡修订建议/K03_S3_S6_K09_2026-11-15.md` §三。
**在三人签字前，改身份证规则前必须先问 C**：动掉生日门禁，`image-dev-031`
会立刻变成一条"误报"；把门禁改成"生日非法一律不报"，`image-lock-014`
会变成漏检。

> **2026-11-08 更正**：这里原来把 `image-lock-014` 也算进"依赖日期门禁"的名单，**那是错的**。
> A 的丢弃分支有前置条件 `check == "pass"`——校验位失败时不看日期，一律报 `fail`(risk 2)。
> lock-014 的校验位也是失败的，所以它本来就会被报出来，是**正例**，已迁标注并重封。
> **只有 dev-031 依赖日期门禁**（它校验位算对了，只有生日非法能挡）。

**另一条纪律**：负例的 bbox 框住**整串号码**，不要只框前几位——否则检测器报出完整号码时，
框对不上，这条负例就白设了。
