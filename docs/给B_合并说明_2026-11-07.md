### 1.2 Decision 全局 revision + 补框 revision —— 已修

#### (a) Decision 的 revision 改成全局版次

你的判断是对的：混合 revision 会被 `validate_records` 直接拒。

```python
old_rev = max((int(p.get("revision") or 0) for p in prev.values()), default=0)
changed = set(targets) != set(prev) or any(
    prev.get(fid, {}).get("action") != action for fid, action in targets.items()
)
revision = 1 if not prev else (old_rev + 1 if changed else old_rev)
```

语义：

| 情况 | 结果 |
|---|---|
| 首次生成 | 全部 `revision=1` |
| 相同输入再生成 | 幂等，全部不变 |
| **任一 finding 改动** | **全部升到同一个新版本**（没变的也升） |
| finding 集合增删 | 也算变化，同上 |

测试加了一条硬断言，防止以后有人改回去：

```python
self.assertEqual(len({r["revision"] for r in second}), 1,
                 "剩余所有 Decision 必须共享一个 revision")
```

#### (b) 补框的版次：新增 `manual_boxes_revision`

你说补框增减或改坐标会改变 `RedactionPlan`，但 `Decision.revision` 看不见——对。
`revision` 只跟踪勾选，补框不经过 Decision。现在交接包多一个字段：

```json
"manual_boxes_revision": "sha256:1a2b3c4d5e6f"
```

**它是内容指纹，不是计数器。** 这不是偷懒，是刻意的：

| 方案 | 问题 |
|---|---|
| 计数器（`1,2,3…`） | 存在界面会话内存里，**程序一重启就归零**。你会看到上一批 `revision=5`、这一批 `revision=1`，误判成「更旧的包」 |
| 内容指纹（现在这个） | 框一样就是一样，改一个像素就变。跨会话、跨机器都成立 |

判定方式：

| 情况 | 值 |
|---|---|
| 两次导出、框没动 | **相同** |
| 改任一坐标 / 换 `method` / 增减框 | **不同** |
| 没有补框 | `sha256:4f53cda18c2b`（固定值，不是缺字段） |

两条刻意的取舍：

- **`id` 不参与**：删掉一个框再加回来会拿到 `manual-002`，但坐标和手法没变，
  对你的计划区域来说不是新批次。
- **`method` 参与**：同一块区域从 `solid` 改 `mosaic`，坐标没变但遮盖效果变了，
  必须算新批次，否则你的复检报告会对着错误的遮盖方式。

**它不进 schema**：`manual_boxes` 本来就不是契约记录（是构造计划的素材），
所以加这个字段不需要改已冻结的 v4 schema，也不需要三人表决。

**你构造计划时怎么用**：

```python
# 同一批：直接复用上次的计划与复检报告
# 不同批：按新的 boxes 重建计划区域，旧的 VerificationReport 作废
```

## 4. 接口契约（构造计划时要用到的）

### 4.1 Detection 必填

| 字段 | 约束 |
|---|---|
| `kind` | `text` / `qr` / `face` / `meta` |
| `subtype` | 必须在该 kind 的枚举内，且**语义匹配**（`face` 固定为 `face_region`，不是 `face`） |
| `bbox` | `[x,y,w,h]` 整数，图像内；**meta 必须为 `null`**，其余非空 |
| `detector_score` | `0..1` 或 `null`。规则类**保留上游 OCR 置信度**，不要为了"规则无概率"抹成 null |
| `risk` | 1 / 2 / 3，见 §5 的分值现状 |
| `details` | 白名单字段，`additionalProperties: false` 会拒多余键 |

### 4.2 Decision

五个字段：`contract_version` / `record_type` / `finding_id` / `action` / `revision`。
`action` 只有 `redact` / `retain`，**没有 skip / selected**。
`revision` 是**全局版次**（§1.2a）。

### 4.3 交接包结构

```json
{
  "contract_version": "photocheck/v4",
  "image_id": "image-dev-001",
  "decisions": [ {"contract_version","record_type","finding_id","action","revision"}, ... ],
  "manual_boxes": [ {"id": "manual-001", "bbox": [x,y,w,h], "method": "solid"}, ... ],
  "manual_boxes_revision": "sha256:1a2b3c4d5e6f",
  "note": "metadata 始终整图清除，不含 Decision；manual_boxes 仅供构造 RedactionPlan"
}
```

- `decisions` 是**合法契约记录**，能直接过 `validate_records`
- `manual_boxes` **不是**契约记录，是给你构造 `finding_id=null` 计划区域的素材
- 若界面那头状态不干净，会多一个 `dropped_foreign_decisions: <int>`——
  看到它说明有别的图的决定被过滤掉了，**数量写进文件是为了让你看见，不是让你忽略**

### 4.4 每个非 meta Detection 恰好一条 Decision

这是 `build_redaction_plan` 的硬校验，C 侧保证：

```python
if decided_ids != actionable_ids:
    raise ContractError("every non-metadata Detection requires exactly one Decision")
```

**meta 一条 Decision 都不产**（元数据始终整图清除）。C 的审计 `RD-01` 每次都在验这件事。

### 4.5 `run_full_recheck=True` 必须显式传

你的默认值已经改成 `True` 了，很好。但我仍然建议**正式入口不给默认值**：

```
逐区域复检 passed → 框外残留没人看 → 报告写"未发现残留" → 用户以为整张图安全
```

理由不是"防御性编程"，是**漏传的后果不对称**：多跑一次只是慢几秒；
漏传一次，用户拿到的是"报告说通过、实际有残留"的文件。
