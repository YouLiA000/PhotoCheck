## 3. K-03 口径：我同意你的判断，并补两个数

### 3.1 你的数我复现了

你给的：预热后 dev-001 双尺度 **1764.9 ms**、单尺度 1293.6；38 张 `repeat 1` **中位 1554.8 / p95 2447.7 / 最慢 2558.1**。

我这边（Ryzen 9 8945HX，接电源，A v2 引擎）：

| 口径 | 中位 | p95 | 最慢 | 超 2023.6 的图 |
|---|---:|---:|---:|---:|
| **每张跑 1 次**（同你的 repeat 1） | 2088.1 | 2979.4 | 3380.9 | **21 / 38** |
| **每张跑 2 次取第 2 次** | **1681.9** | **2125.6** | **2205.1** | **3 / 38** |

### 3.2 你没提的那个因素：**每张图的第一次都有额外开销**

同一张图连跑三次：

```
image-dev-009:  3258 → 1448 → 1418 ms
image-dev-002:  2758 → 1701 → 1676 ms
```

**差 2.3 倍。** 这不是进程级模型加载（进程已经预热过），是**换图时的重新分配**——
RapidOCR 的 det/rec 输入尺寸随图变化，每次换尺寸都要重建。

所以 `--repeat 1` 测到的是"冷图"，不是稳态。**你的 1554.8 里也混了这一层**（方向一致，量级不同）。

**这解释了为什么"每张跑一次"会得出"55% 的图超线"，而跑两次只剩 8%。**

### 3.3 建议 K-03 这么写（不改阈值，只定统计口径）

```
K-03 性能验收（预热后稳态）
  测量方法：
    1. 进程预热 1 次（模型加载不计）
    2. 每张图先跑 1 次作废（换图开销不计），第 2 次开始计时
    3. 报告三个数：median / p95 / max，并注明 CPU、电源状态、样本数

  判据：
    median ≤ 1.2 × 基线（2023.6 ms）   ← 硬线
    p95    ≤ 1.5 × 基线（2529.4 ms）   ← 软线，超了要说明
    max    不设硬线，但必须报出来
```

用这个尺子量两边的数据：

| | median | p95 | max | 结论 |
|---|---:|---:|---:|---|
| B（你的机器） | 1554.8（0.92×） | 2447.7（1.45×） | 2558.1 | ✅ 两项都过 |
| C（这台机器） | 1681.9（1.18×） | 2125.6（1.26×） | 2205.1 | ✅ 两项都过 |

**为什么不同意"逐图上限"**：单张最慢受图内容影响（密集版面、多文字块），
逐图卡 2023.6 等于要求"所有图都和最简单的图一样快"。这会逼着大家去把 3 张慢图调下来，
而它们的慢是真实的复杂度，不是缺陷。

**为什么 max 不设硬线**：p95 已经管住长尾；max 单点波动大（±30%），设硬线会变成运气测试。
但必须报，因为"最慢那张有多慢"是用户能感知的。

## 6. 三个接口问题：全部确认，且已经在这么跑

### 6.1 入口与签名

与你说的一致。C 的 `app/service.py` 就是按这个过程调的：

```python
with ingest_image(path, image_id=image_id) as ingested:
    envelope = analyze_a(ingested.image, image_id, kinds=("text", "qr", "face"))
    detections = [*ingested.detections, *envelope.detections]
    plan = build_redaction_plan(descriptor, detections, decisions,
                                revision=1, manual_regions=manual_regions,
                                method_by_finding={fid: method for fid in chosen})
    result = process_and_export(ingested, plan, output_dir=out_dir,
                                detections=detections, decisions=decisions,
                                exiftool_path=_EXIFTOOL, run_full_recheck=True)
```

一个差异要说明：**`revision` 我用的是 `1`，不是 `max(decision["revision"])`**。
因为 C 侧现在所有 Decision 都是同一全局 revision，恒为 1；
等我加了"重新处置"功能、revision 会递增时，再按你写的取 `max`。
现在的写法在 revision=1 时与你的等价，不会把 SHA 字符串写进 `RedactionPlan.revision`。

### 6.2 进程内 vs 子进程

**用进程内**，和你推荐一致。C 的应用是 `http.server` 单进程，直接调 `process_and_export`
拿结构化 `ProcessingResult`，没有 stdout 解析。

跨仓库路径：C 的应用把引擎 vendored 到 `app/vendor/photocheck`，所以不需要 `PHOTOCHECK_REPO_ROOT`。
审计器 `RD-01` / `DET-01` 支持设这个变量来跨仓库验你的入口。

### 6.3 R-03 字段

确认：v4 `VerificationCheck` 只有 `region_id / status / method`，没有 `probe_kind`。

映射关系我记下了：

```
probe_kind  → verification.checks[].method
residual 数 → verification.residuals[]
整图漏检    → ProcessingResult.full_recheck
```

C 的应用现在读的就是这三个位置（`checks[].method`、`residuals`、`full_recheck.unplanned_count`）。
