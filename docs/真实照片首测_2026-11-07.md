> **素材**：14 张，作者本人拍摄，内容全部虚构
> **检测器**：A 第三版（B vendored 的 `photocheck/detectors/a_engine`，213 passed）
> **口径**：`analyze(kinds=("text","qr"))`，原图不缩放不预处理
> **目录**：`dataset/real/`（已 gitignore，清单 `manifest.csv` 同样不入库）
> **本文件不含原图与完整号码**，只给统计与掩码示例

## 三、三个发现，按严重程度排

### 1. 二维码：屏幕翻拍下全灭，而且不是"阈值调一调"能救的

`real-008` 是两张打印出来的大二维码，肉眼清清楚楚，**检出 0 条**。

我做了区分实验（这一步很重要，决定责任归属）：

```
cv2.QRCodeDetector().detect()        → 找到四角坐标（True）
cv2.QRCodeDetector().detectAndDecode → 返回 None
pyzbar.decode                        → 0 条
透视矫正到 600×600 + Otsu / 自适应二值 → 仍然 0 条
```

矫正后的图我看过：三个定位角完整、对齐图案在、模块排列像真码，
**但整张图布满竖向摩尔纹**，模块边界被干扰到无法采样。

**结论**：这不是检测器没写对，是**屏幕翻拍这种输入本身不可解**。
判据已经尽力（能找到四角说明几何没丢），坏在像素。

**报告里该怎么写**：

> 二维码在合成集 100% 可解；在**屏幕翻拍**场景 0/5 可解，原因是摩尔纹破坏模块采样。
> 纸张实拍的二维码未测试，不能据此推断"二维码检出不可用"。

**不要**写成"检测器在真实照片上失效"——那是过度归因，评审一问就露。

### 2. 一个号码报成两条，而且框跨了两行

`real-001` 面单上 `139` 开头的收件人号码只有**一处**，检测器给了**两个框**：

```
bbox=[772,775,245,268]   掩码 139****5678
bbox=[1131,775,245,268]  掩码 139****5678
```

两个框各 245×268——268 的高度对一行字来说太高了（正常一行约 40–130）。
放大看：两个框都**竖着跨过了地址行**，一个框住"139-1234-"、另一个框住"5678"。

**这是 A 的 K-03「同行合并」在相邻行上的失效**：它把电话号码行和下面的地址行
合成了两块，然后两块都读出同一个号码。

**后果不是指标难看，是流程出错**：

- C 的界面会为同一个号码生成**两条 Decision**；
- B 的 `build_redaction_plan` 会排**两个遮盖区域**，其中一个盖着地址；
- 计数、误报率、遮盖面积全部被污染。

`real-004` 同样症状（也是同一个 `139` 号码被拆成两个框）。

### 3. 手写体：读错末几位，但照常上报——比漏检更危险

`real-014` 的访客登记表上，`1101…1234` 被检出，**框很准，位数也读对了**，
但 `masked_preview` 是 `1101**********4010` —— **末四位变成了 4010**。

同一张图上另一个证件号 `3201…0789` **完全没检出**；手写的手机号也没检出。

**为什么这条最危险**：它不是"没找到"，是**找到后报了一个不存在的号码**。

- 用户看到 `1101**********4010`，会以为自己这张照片里是这个号；
- 这条 Decision 被 `redact` 后，遮盖位置对（bbox 准），但**报告里的掩码是假的**；
- 更麻烦的是 `idcard_check` 是基于错号码算的，`fail` 这个结论**碰巧对了**，
  下次可能就错了。

## 四、给 A 的三条（可直接转）

| # | 问题 | 证据 | 建议 |
|---|---|---|---|
| 1 | 相邻行合并导致**同一号码重复上报**、框跨行 | `real-001` / `real-004`：同一号码两个 245×268 框 | 合并后若两块的文本规则命中结果相同且框重叠 >30%，合并成一条；框高超过行高 2.5 倍时按行切分 |
| 2 | 手写体数字误读，掩码与校验都基于错值 | `real-014`：实际 `…1234`，掩码 `…4010` | 对 `idcard` / `phone` 这类**强格式**对象，OCR 置信度低的位数不要直接采信；至少在 `details` 里标 `low_confidence: true`，让界面能提示"请人工核对" |
| 3 | 二维码在摩尔纹下不可解 | `real-008` 等 5 处 | 不是 bug，是输入限制。建议 `probe` 的 `unavailable`/`undecodable` 语义保留，报告里写清场景 |

## 五、这批素材改变了什么

| 改动 | 说明 |
|---|---|
| 报告的"局限"一节有了实测依据 | 原来只能写"未在实拍上验证"，现在能写具体数字与原因 |
| 合成集的 100% 降级为"合成集指标" | 不再暗示泛化能力 |
| 新增两个 badcase 候选 | `real-001` 的重复上报、`real-014` 的误读掩码。前者建议 A 归档 BC，后者建议进 badcase |
