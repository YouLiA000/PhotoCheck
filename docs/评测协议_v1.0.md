# PhotoCheck 评测协议 v1.0

> 制定：2026-11-02 ｜ 角色：C ｜ 对应实现：`eval/`（`config.py` / `matcher.py` / `metrics.py` / `reporter.py`）
> 依据：《功能规格卡 v1.4》K-13、§0.4 DoD、§0.5 措辞红线
>
> **这份文档是"必交成果 2：评测协议与脚本"的一半。**改这里任何一条等于改评测标准，
> 需要三人同意并升版本号（见 §9）。文档与代码不一致时**以代码为准并改文档**——
> 一份和实现对不上的协议，比没有协议更糟。

## 1. 这份协议解决什么

同一份数据集、同一个检测器，换一套匹配口径就能得出"召回 95%"和"召回 62%"两个数。
所以结论要能复核，必须先固定四件事：

1. **哪些图能跑**（§2 集合纪律）
2. **什么叫"检对了"**（§4 匹配规则）
3. **指标怎么算、分母是什么**（§5）
4. **什么样的结论不许下**（§7 报告纪律）

## 2. 集合纪律

| 集合 | 张数 | 用途 | 谁来跑 |
|---|---|---|---|
| `dataset/dev` | 40 | 日常调试、调参、看效果 | 随时 |
| `dataset/lock` | 23 | 只在 W8 / W20 / 答辩前各跑一次 | 冻结版本后 |

三条硬规矩：

- **lock 不参与调参**。跑完不许"改一版算法再跑一次"——那是自己给自己出题又改答案。
- **模板必须与 dev 零交集**。lock 用 invoice / badge / admission，dev 用 receipt / chat /
  card / notice / broken。共用模板等于把答案提前给模型看过，锁了也白锁。
  由 `test_lock_templates_disjoint_from_dev` 守着。
- **lock 按字节封存**。`dataset/lock/SHA256SUMS.txt` 覆盖图片、标注、清单共 48 个文件，
  `SEALED.json` 额外记录 sums 自身的哈希。跑之前先 `python dataset/tools/seal_lock.py verify`，
  不为 0 就说明数据集被改过，**这一轮的数不能用于结论**。

## 3. 输入格式

### 3.1 真值

`dataset/<set>/labels/<image_id>.json`，每条是契约 v4 的 `Detection`：
`id` / `image_id` / `kind` / `subtype` / `bbox` / `detector_score` / `evidence` / `risk` / `details`。

`kind=meta` 的对象 `bbox` 必须为 `null`；它描述的是"这张图带 GPS"这类整图属性。

误报判据不在真值里，在 `dataset/<set>/negatives.json`：**"像手机号但不是"的区域**
（订单号、座机、少一位、工号、非法日期流水号、19 位卡号）。它们不是 Detection，
因为契约只描述"检出事实"，不描述"这里什么都没有但很容易被误判"。

### 3.2 预测

`--pred-dir` 指向一个目录，文件名 `<image_id>.json`，内容是该图的 `Detection` 列表。
A 的检测器直接按契约输出即可；`--perfect` 用真值当预测（自测，见 §8.1）。

**预测会先过契约校验，不合格直接拒绝（退出码 2），不进入评分。** 这条不是洁癖：
少一个 `subtype` 会被算成"这张图什么都没检出"，召回掉到 0，然后两个人去查算法。
格式问题必须在入口就和检测问题分开。

除契约校验外，还有两条**对齐检查**，同样退出码 2：

| 检查 | 不通过的后果（若不拦） |
|---|---|
| 文件名必须等于记录里的 `image_id` | 分组键与真值对不上，整批落空 |
| 预测的 `image_id` 至少要与数据集有交集 | 同上，且提示为零——看起来像"检测器完全失效" |

这两条是 W5 最容易踩的坑：A 的输出只要有一处拼写不同，指标就是 0 分而脚本正常退出。
0 分比报错更难查，所以宁可在入口拒绝。

**覆盖率会写进报告**：预测覆盖了几张真值图、有多少张预测对不上数据集。覆盖不全时
报告顶部会有一条 ⚠ 提示——下面的指标只代表"已对齐的那部分"，不能当成全集结论。

## 4. 匹配规则

### 4.1 主口径（唯一进主表的）

> **IoU ≥ 0.5 且 `subtype` 相同，且一对一。**

- IoU < 0.5 视为没对上；
- 框对上了但 subtype 不同 → **计入 `subtype_error`**，既不算 TP 也不算 FN/FP；
- **一对一**：一个真值框只能被一个预测框匹配，反之亦然，按 IoU 从高到低贪心配对。
  不做这一步，模型对同一处输出 5 个框就能把召回刷上去。

### 4.2 元数据的特例

`kind=meta` 没有 bbox，按 `subtype` 在**整图范围内**计数配对：真值有 3 条 meta、预测有
2 条且 subtype 相符，则 TP=2、FN=1。同一 subtype 多报的算 FP。

### 4.3 宽口径只做敏感性分析

文本行是细长条，OCR 的框常比字形框大一圈，卡 0.5 会偏严。所以额外提供
IoU ≥ 0.3（`config.LOOSE_IOU_TEXT`）的一档，**只进附录，不进主表**。

主结论只认 0.5，否则别人按规格卡复现时对不上。附录要写清"换 0.3 后 X 从 A 变到 B"。

## 5. 指标定义

设某 subtype 的真值对象数为 `n`：

```
n        = tp + fn + subtype_error
n_pred   = tp + subtype_error + fp
recall   = tp / n
precision= tp / n_pred
```

**为什么 `subtype_error` 进分母**：这些对象确实存在于图中，检测器也框对了位置，只是把
手机号判成了身份证号。它们既不该让召回变好看（不是正确检出），也不该被算成误报
（框是对的）。单列一列的同时计入分母，得到的才是"这一类到底判对了多少"。

总表另给四个数：

| 指标 | 定义 | 用途 |
|---|---|---|
| `objects_truth` | `tp + fn + subtype_error` | 分母可核对 |
| `objects_pred` | `tp + subtype_error + fp` | 分母可核对 |
| `fp_per_image` | `fp / 图数` | K-13 明确要求 |
| `negative_hits` | 误报中落在 `negatives.json` 区域内的个数 | 回答"是不是被'像但不是'骗了" |

`negative_hits` 是诊断量，不进主表：它高说明正则太松，它低说明误报来自别处（背景纹理、
表格线），两种问题的修法完全不同。

### 5.1 不确定性：必须带区间

点估计在小样本上极不稳：n=68 时报 0.94，少错一个对象就是 0.96，多错一个就是 0.93。
所以报告同时给 **95% 置信区间**，用**按图重采样**的 bootstrap（cluster bootstrap）：

- 为什么按图而不是按对象：同一张图里的对象高度相关（同版式、同光照、同一次压缩），
  按对象重采样会把区间算窄，看着"很确定"，其实不是；
- 默认 1000 次、固定种子（`--seed 7`），**同样输入必须得到同样区间**，否则不可复现；
- `--ci 0` 可关闭，但正式报告不得关闭。

这条**不改变**点估计的定义，只是把"这个数有多准"一起报出来。

### 5.2 分层：难度贡献必须可见

按 `manifest.csv` 的 `difficulty` 出 easy / hard 两张表（台账里没有难度的归 `unknown`，
不偷偷并进 easy）。理由：总表一个 0.95，可能是 40 张清晰正拍撑起来的，也可能是困难
样本真的解决了——两种结论对项目的意义完全不同，混在一起就说不清。

分层表与总表**同口径**，不是另一套指标。

## 6. 三层评测

| 层 | 对象 | 状态 |
|---|---|---|
| 第一层 检测质量 | 处理前的 Detection | ✅ 已实现 |
| 第二层 脱敏有效性 | **最终导出文件**（不是中间图） | 结构与表头已就位，等 B 的 K-08/K-09 |
| 第三层 过度脱敏 | 最终导出文件 + 人工判读 | 同上 |

第二层必须是最终导出文件：中间处理图上"看不见了"，导出时重编码、重采样可能把边缘
细节带回来。在中间图上测出来的残留率是假数。

第二层的残留原因必须**三分类**：`漏检`（第一次就没发现）/ `保留`（用户主动 retain）/
`遮挡失败`（遮了但没遮住）。三者混成一个数，就无法回答"到底是检测的锅还是处置的锅"。

## 7. 报告纪律

1. **每个指标必须带 n**。`eval` 已自动在 n < 30 的行上标「仅作开发参考」。
2. **n < 30 不得下通用结论**。禁止用 3 个样本推"召回 80%"。
3. **不得把 `detector_score` 写成概率**。它是排序与过滤用的分数，不是校准概率，
   报告里不许出现"93% 概率是隐私信息"。
4. **不得宣称"没有漏检"**。同模型复检只能证明"这个模型不再读出"，看不见它本来就看不见的。
   合规写法：「在 N 张样本中发现 M 处首次漏检」。
5. **不得做安全承诺**。禁用「已确保安全」「可以放心分享」「无隐私风险」。
6. **合成集与实拍集分开报**，不许混算平均。合成图无拍摄角度、文字偏清晰、不含人脸，
   在上面得到的指标偏乐观，报告必须写这句。

## 8. 复现步骤

```bash
# 0. 环境（缺什么会直接说）
python tools/check_env.py

# 1. 跑之前先验封存，非 0 就别跑
python dataset/tools/seal_lock.py verify

# 2. 第一层：dev
python eval/eval.py --set dev --pred-dir <预测目录> --out results/

# 3. 锁定集（只在 W8 / W20 / 答辩前）
python eval/eval.py --set lock --pred-dir <预测目录> --out results/
```

结果落到 `results/<时间戳>-<git短sha>/`，含：

| 文件 | 内容 |
|---|---|
| `detection_quality.csv` | 第一层主表，分 subtype 带 n |
| `detection_by_difficulty.csv` | 同口径，按 easy / hard 分层 |
| `failure_cases.csv` | **逐条**失败明细：漏检 / 误报 / 类别判错，带 image_id、bbox、IoU |
| `redaction_validity.csv` · `over_redaction.csv` | 第二、三层（结构就位，等 B） |
| `summary.json` | 机器可读的全量结果，含 CI 参数 |
| `README.md` | 人读版，含区间与分层表 |

**不覆盖历史结果**——基线表要能对比两次提交。

`failure_cases.csv` 是给 A 的 R-02 用的：只给计数，A 拿到报表也不知道该改哪一段；
给出逐条明细（含 bbox 与 IoU），才能直接进失败案例库按 subtype 归档。

### 8.1 脚本自证（每次改 eval 代码后必跑）

```bash
python eval/eval.py --set dev --perfect
```

拿真值当预测，**所有指标必须是 1.0**（当前 dev 为 TP=84 / FN=0 / FP=0 / 判别错=0）。不是 1.0 就是
评测代码写错了，不许往下走。这是 A 的检测器交付之前，唯一能证明评测脚本本身正确的手段。

反向验证：故意漏 3 个手机号 + 判错 1 个证号 + 2 张干净图各塞 1 个假框，应得
**TP 80 / FN 3 / FP 2 / 判别错 1，召回 0.9524（80/84）、精确 0.9639（80/83）**。
分母可手算核对：`objects_truth = 80+3+1 = 84`，`objects_pred = 80+1+2 = 83`。
对不上就说明匹配或统计有一处写错了。

## 10. 已知局限（写报告时必须一起交）

1. **只评测"本工具定义的"四类线索**：手机号、身份证号、二维码、敏感元数据。
   图里其他个人信息不在评测范围，低分不代表图安全。
2. **没有人脸样本**。K-07 未做，人脸一栏为 `not_applicable`，不是 0 分也不是满分。
3. **合成样本占绝大多数**。见 §7 第 6 条。
4. **第二、三层尚无数据**。等 B 的 `redact()` / `verify()` 交付后补测；
   在那之前，任何"脱敏有效性"的说法都没有本协议支撑。
