**建议你在 README 里这么写**：
> 如果 `check_env` 报 pyzbar 不可用且错误是"找不到模块 xxx.dll（或它的某个依赖）"，

> 「Visual C++ Redistributable for Visual Studio 2013 (x64)」即可，不需要重装 wheel。

这样别人遇到同样问题时不会去重装 pyzbar（那条路永远无效）。

**另外你试 `cv2.barcode.BarcodeDetector` 全部解不出这件事，价值很大**——它排除了一个"看起来能用"的

## 4. D-1 我实测后决定**不执行**——这条要和你的"同意"对一下

你表决同意 `mediapipe==0.10.14`。我按这个执行了，**结果发现问题，已回滚**。

### 实测过程

```bash
pip install "mediapipe==0.10.14"
```

输出：

```
Successfully installed jax-0.10.2 jaxlib-0.10.2 mediapipe-0.10.14 ml_dtypes-0.6.0
                       numpy-2.4.6 opt_einsum-3.4.0 scipy-1.17.1
```

**它把 numpy 1.26.4 升级到了 2.4.6**，还带进 jax / jaxlib / scipy（~200 MB）。

### 为什么这是问题

- `requirements.txt` 明确锁 `numpy==1.26.4`，注释写着「mediapipe is unstable on numpy 2.x」
- `opencv-contrib-python==4.10.0.84` 是针对 numpy 1.x 编译的，numpy 2.x 有 ABI 风险
- 装完之后功能**确实还能跑**（我测了 `imencode` / `GaussianBlur` / `QRCodeDetector` 都正常），
  但这只是表面正常，边缘路径没测过

### 回滚与清理

```bash
pip install "numpy==1.26.4" "mediapipe==0.10.35"
pip uninstall -y jax jaxlib ml_dtypes scipy opt_einsum
# 清掉 ~rotobuf 残留
```

**已验证恢复**：numpy 1.26.4 / cv2 4.10.0 / mediapipe 0.10.35（无 solutions）/ rapidocr 可导入 / 全套测试通过。

### 我的结论：**接受 face 不可用，不换 numpy**

| 收益 | 代价 |
|---|---|
| face 检测可用（K-07） | numpy 全局升到 2.x |
| K-09d 人脸复检可用 | jax / jaxlib / scipy 进环境 |
| | 与 `numpy==1.26.4` 的既定决策冲突 |

**C 的合成集没有任何人脸样本，且无合规来源。** 为一个"永远返回 `not_applicable`"的检测器
把全局数值库升一个大版本，性价比是负的。

**所以 `requirements.txt` 现在的写法是**：

```txt
mediapipe==0.10.35   # 实际版本。0.10.35 无 solutions → face 不可用 → K-07/K-09d 走 not_applicable。
                     # 不要装 0.10.14 去换 solutions：实测会拖进 numpy 2.4.6 + jax/jaxlib/scipy。
```

**如果你的环境（`C:/venvs/photocheck`）已经跑着 0.10.14 + numpy 2，那没问题**——那是独立 venv，
不影响你的检测器。但**请不要把"face 可用"当成团队共识**，C 和 B 的环境都不可用。
