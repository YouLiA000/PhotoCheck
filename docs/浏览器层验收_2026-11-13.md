## 验收中发现并修复

1. 修改勾选、补框或遮盖方式后，旧复检报告仍然显示。
   - 修复：任何决定变化递增 `revision`，立即隐藏旧报告和结果标签页。
2. 手动区域的复检方法被错误显示为“语义待确认”。
   - 修复：映射为“整块复核”。
3. 页面调用处置接口时没有携带具体 `analysis_id`。
   - 修复：前端携带 `analysis_id`，服务端按该快照处理，避免多个标签页串图。
4. 服务端固定使用 `revision=1`。
   - 修复：前端发送当前 revision，Decision 和 RedactionPlan 使用同一值；服务端拒绝版本倒退。

## 性能

原便携包首次选择示例时实测：

```text
检测总耗时：23.7 秒
其中 text：21.2 秒
```

原因不是稳定推理能力，而是微小空白图预热没有覆盖实际尺寸，用户第一次请求仍在构建大图 OCR 图。

优化措施：

- 服务启动时使用 1000×1400 的真实示例完成同步预热；
- 预热和用户检测共用检测器锁，避免两个 OCR 推理同时初始化；
- JSON Schema 和 jsonschema validator 在进程内只编译一次；
- 前端携带稳定的 `analysis_id` 与 revision；
- 服务端拒绝旧 revision 的处理请求。

优化后同一界面实测：

```text
首次上传检测：4.0 秒
text / qr / face：3537 / 158 / 20 ms
二维码 + 手动框处置：3.0 秒
```

另外，直接基准中“文本 + 两个二维码 + 手机号”的完整处置由约 8.7 秒降到约
5.1 秒。处置耗时随计划区域和是否含文字变化，不应对外承诺固定秒数。

在后续负载较高的重复测量中，内置运行时单次检测出现约 5–9 秒的波动。
这说明当前机器存在 CPU 抢占、磁盘扫描或温控影响；上表是一次受控界面验收的
实测值，不是性能承诺。稳定结论是：模型只在启动时加载，Schema 不再逐记录重复
编译，用户请求也不会与后台预热并发。

## 边界

- 本结果来自当前开发机和合成图片，不代表所有机器、所有图片都能达到该速度。
- `passed` 仅表示当前计划区域未发现可复检残留，不是安全承诺。
- 未选择的二维码仍会出现在导出图中，并由整图复检查出、页面明确警告。
