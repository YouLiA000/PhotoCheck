## 六、C 的 Decision revision 与 B 契约不兼容

### 6.1 C 当前行为

`ui/decision.py` 只在某个 finding 的动作发生变化时修改该条 Decision 的 revision：

```text
未变项：revision 保持 1
改变项：revision 变成 2
```

C 的测试 `test_deselect_produces_retain_and_bumps_revision` 明确要求这种混合 revision。

### 6.2 B 当前契约

B 的 `validate_records()` 要求：

```text
all current decisions must share one revision
```

`build_redaction_plan()` 还要求每条 Decision 的 revision 等于当前计划 revision。

因此：

1. 首次全部勾选时，C 的 payload 可用；
2. 用户取消一项后，C 会导出 revision 1 和 2 混合的记录；
3. B 的 v4 校验会直接拒绝该交接包。

这是最小界面修改选择后的真实阻塞，不能只靠首次演示绕过。

### 6.3 需要的修正

如果采用“全局版本号”语义，C 应：

- 维护一个当前全局 revision；
- 任一 Decision 改变时，`revision += 1`；
- 重新导出时，把所有当前 Decision 都写成同一个新 revision；
- 旧 VerificationReport 随 plan revision 变化失效。

C 测试应从“只有变化项递增”改为“任一变化后全部当前决定共享新 revision”。

### 6.4 手动补框也影响 revision

当前 C 的补框状态变化不会递增 revision。

但补框会改变 RedactionPlan，因此：

- 增加补框；
- 删除补框；
- 修改补框坐标或处置方式；

都应生成新的计划 revision，使旧复检结果失效。

C 的 `.state` 应同时跟踪 decisions 和 manual boxes 的版本。

## 七、B 已完成的接口修正

### 7.1 支持稳定数据集 image_id

原实现：

```python
with ingest_image(path) as ingested:
    # image_id 总是 image-{source_sha256[:24]}
```

该行为无法与 C 的 `image-dev-001` 预测文件名对齐。

现已支持：

```python
with ingest_image(path, image_id="image-dev-001") as ingested:
    ...
```

规则：

- 显式 ID 必须满足 v4 Identifier；
- 非法 ID 抛 `ImageIngestError`；
- 未显式传入时继续使用内容哈希默认值。

### 7.2 整图重检默认开启

`process_and_export()` 的 `run_full_recheck` 默认值已从 `False` 改为 `True`。

正式调用仍应显式写出：

```python
run_full_recheck=True
```

这样代码审查时能看出 C 没有依赖默认值。

### 7.3 C 数据集运行脚本

新增：

```text
photocheck/scripts/run_c_dataset.py
```

用法：

```powershell
python photocheck\scripts\run_c_dataset.py `
  D:\path\to\handoff\dataset `
  --split dev `
  --image-id image-dev-001 `
  --output-dir D:\path\to\integration-output
```

特性：

- 使用图片文件名作为 C 的稳定 `image_id`；
- B meta 与 A text/qr/face 合并；
- 默认对全部非 meta 对象执行 solid 脱敏；
- 强制执行逐区域和整图复检；
- 每图生成结果；
- lock 必须显式传 `--allow-lock`，防止误跑封存集。
