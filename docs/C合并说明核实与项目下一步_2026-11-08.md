## 三、`image-lock-014` 结论错误

### 3.1 C 的主张

C 认为该样本生日段非法，因此应永久作为负例，不需要修改 lock。

### 3.2 B 的实际复验

C 给出的号码是：

```text
1101**********9343
```

当前 A 实体规则输出：

```text
subtype: idcard
risk: 2
idcard_check: fail
masked_preview: 1101**********9343
```

直接对 lock 图片 `image-lock-014.jpg` 运行 A 的 text 检测，实际输出：

```text
text idcard risk=2
details={'masked_preview': '1101**********9343', 'idcard_check': 'fail'}
bbox=[251,501,287,25]
warnings=[]
```

### 3.3 原因

A 的日期门禁不是“只要生日非法就一律丢弃”。

当前规则是：

| 校验位 | 生日段 | 输出 |
|---|---|---|
| pass | 合法 | idcard / pass / risk 3 |
| fail | 任意 | idcard / fail / risk 2 |
| pass | 非法 | 丢弃，按构造流水号处理 |

`image-lock-014` 同时满足：

- 生日段非法；
- 校验位失败。

按规格卡 K-04“校验失败仍必须报告”和 A 的现状，它会被报成 `idcard_check=fail`。

### 3.4 正确处置

该样本不能继续留在 `negatives.json` 作为负例。

仍应按此前三方同意的方案 A：

1. 图字节不改；
2. 从负例区域迁出；
3. labels 增加 `kind=text / subtype=idcard / idcard_check=fail / risk=2`；
4. 重新封存 lock；
5. 发布新的 `SHA256SUMS.txt`、`SEALED.json` 和包哈希。

在 C 修正前，B 不使用 lock 计算“误报率”，避免把已知标注错误算成模型错误。

## 四、S-6 建议需要改写

```text
18 位候选先检查出生日期段。

```

## 五、OCR 性能核实

### 5.1 C 的冷启动数字

C 报告 `1120×1560` 图片 OCR 需要 5513 ms。


这里包含 RapidOCR 首次模型加载。

### 5.2 预热后数字

同一个 `image-dev-001` 预热后：

```text
双尺度: 1764.9 ms
单尺度: 1293.6 ms
验收线: 2023.6 ms
```

所以 C 的“2.7 倍超线”不能作为稳态结论。

### 5.3 完整旧 dev 预热结果

B 对旧 C dev 的 38 张有效图执行 `bench_ocr.py --repeat 1`：

```text
中位数: 1554.8 ms
p95:    2447.7 ms
最慢:   2558.1 ms
验收线: 2023.6 ms
```

因此准确结论是：

- 中位数达标；
- p95 和最慢图超标；
- 若 K-03 按“逐图必须 ≤2023.6 ms”验收，仍有失败；
- 如果只按中位数验收，则达标。

规格卡必须明确采用“逐图上限”还是“中位数 + p95 门槛”，否则双方会继续用不同口径争论。

### 5.4 单尺度降级暂不采用

单尺度单张测试更快，但完整旧 dev 批次在运行中出现明显异常长尾，最慢达到 6779.6 ms。

本轮没有证据证明关闭双尺度能稳定改善总体性能，也没完成召回等价验证，因此不修改当前 `dual_scale=True`。

## 六、C 两个接口问题的回答

### 6.1 正式入口和签名

入口已经在 manifest：

```text
photocheck/interfaces.json
entries.process
```

解析后为：

```text
photocheck.core.pipeline.process_and_export
```

签名：

```python
process_and_export(
    ingested: IngestedImage,
    plan: Mapping[str, Any],
    *,
    output_dir: str | os.PathLike[str],
    detections: Iterable[Mapping[str, Any]] = (),
    decisions: Iterable[Mapping[str, Any]] = (),
    exiftool_path: str | os.PathLike[str] | None = None,
    content_probe: ContentProbe | None = None,
    run_full_recheck: bool = True,
) -> ProcessingResult
```

C 的完整调用顺序是：

```python
with ingest_image(path, image_id=image_id) as ingested:
    envelope = analyze_a(ingested.image, image_id)
    detections = [*ingested.detections, *envelope.detections]
    decisions = payload["decisions"]
    plan = build_redaction_plan(
        ingested.descriptor,
        detections,
        decisions,
        revision=max(decision["revision"] for decision in decisions),
        manual_regions=payload["manual_boxes"],
    )
    result = process_and_export(
        ingested,
        plan,
        output_dir=output_dir,
        detections=detections,
        decisions=decisions,
        run_full_recheck=True,
    )
```

没有名为 `redact()` 的正式兼容壳。

### 6.2 进程内还是子进程

B 推荐进程内调用。

理由：

- 可以直接拿结构化 `ProcessingResult`；
- C 已经在自己的进程里运行 Gradio；
- `photocheck` 与 C 的 `contract` 包名不冲突；
- 不需要解析 stdout；
- 异常、哈希和复检状态可以直接传给页面。

跨仓库时设置：

```text
PHOTOCHECK_REPO_ROOT=<包含 photocheck/ 的仓库根>
```

并只把仓库根加入 `sys.path`。

子进程可作为隔离环境的后备，不是主方案。

### 6.3 R-03 字段

v4 `VerificationCheck` 实际字段是：

```text
region_id
status
method
```

C 提出的 `probe_kind` 和逐项 `residual_*` 不在该 Schema 中。

因此对应关系是：

```text
probe_kind  -> verification.checks[].method
residual 数 -> verification.residuals[]
整图漏检   -> ProcessingResult.full_recheck
```

`ProcessingResult` 输出：

```text
export
verification
    disposal_state
    checks[]
        region_id / status / method
    residuals[]
full_recheck
    detections / retained_count / unplanned_count / unplanned / warnings
```
