> 生成日期：2026-10-29　｜　修订：v1.1 重新平衡三人工作量，新增 K-15 集成卡

## 0. 怎么用这份文档

1. 每人只认领**自己名下的卡**，卡就是任务单，做完打勾。
2. 每张卡的「验收标准」是**可测的**，不达标不算完成，不许口头说"差不多了"。
3. 每张卡的「工具」一栏写死了用什么库，**不要私自换**（换库 = 三人环境不一致 = 联调灾难）。
4. 每张卡的「降级方案」是**超时保命用**的，不是可选项——超时就降级，不许硬扛。
5. 变更纪律：W8 冻结后，只允许**新增卡**，不允许**改动已验收的卡**。

### 0.2 共享数据契约（三人共同遵守，改动需三人同意）

所有检测器**必须**返回同一种结构，否则 B 和 C 全都没法写。

~~~json
Finding = {
  "id": "f-001",
  "kind": "meta | text | qr | face",
  "subtype": "gps | datetime | device | phone | idcard | tracking | address | wifi | wechat_card | link | face_region",
  "bbox": [x, y, w, h],
  "score": 0.93,
  "text": "原始文本",
  "payload": "解码内容",
  "risk": 3,
  "default_action": "hide"
}
~~~

（bbox 为像素坐标，kind=meta 时为 null；score 为 0~1，meta 类固定 1.0；risk 取值 1/2/3；有码类必填 payload，文字类必填 text。）

复检器返回：

~~~json
Verdict = {
  "passed": true,
  "checks": [
    {"name": "exif", "ok": true,  "detail": "0 个敏感字段"},
    {"name": "qr",   "ok": true,  "detail": "2 个码，均不可解码"},
    {"name": "ocr",  "ok": false, "detail": "残留 1 处疑似手机号"},
    {"name": "face", "ok": true,  "detail": "0 张可检测人脸"}
  ],
  "residual": [],
  "risk_level": "low | medium | high"
}
~~~

### 0.3 工具总表（**版本必须锁进 requirements.txt**）

| 环节 | 工具 / 库 | 建议版本 | 为什么是它 |
|---|---|---|---|
| 运行环境 | Python | **3.11** | mediapipe / rapidocr 的 wheel 在 3.11 最稳，3.13 会缺轮子 |
| 依赖隔离 | venv + requirements.txt | — | 第一天就锁，防"我电脑能跑" |
| 界面 | **Gradio** | 5.x | 自带 AnnotatedImage / ImageSlider，画框和对比滑块白送 |
| 图像读写 | Pillow | 10.x | 读 EXIF、重建导出 |
| HEIC 支持 | pillow-heif | 0.18+ | iPhone 照片，**可选，装不上就跳过** |
| 图像处理 | opencv-python | 4.10.x | 预处理、重采样、模糊、马赛克 |
| EXIF 读写 | piexif | 1.1.3 | 字段级读取 / 删除 |
| EXIF 核验 | **ExifTool**（命令行） | 12.x+ | 独立第三方核验，是"复检"的证据 |
| OCR | **RapidOCR**（rapidocr-onnxruntime） | 1.4.x | 不要 torch、不要 paddle，pip 装完即用，中文强 |
| 二维码 | pyzbar | 0.1.9 | Windows wheel 自带 DLL，能用 |
| 二维码兜底 | cv2.QRCodeDetector | 随 OpenCV | pyzbar 解不出时至少给个框 |
| 人脸 | mediapipe | 0.10.x | 正脸够用，安装简单 |
| 数值 | NumPy | 1.26.x | mediapipe 对 2.x 兼容不稳，压 1.26 |
| 打包 | PyInstaller | 6.x | 最后一周才做，做不成给 bat 也行 |
| 抓包取证 | 资源监视器 / Wireshark | — | 只用于离线证明截图 |

> **禁用的东西**：PaddleOCR（依赖几个 G，大一装到放弃）、PySide6（上手慢）、任何需要联网的 API、任何 LLM 依赖。

| 项 | 内容 |
|---|---|
| 负责人 | **B** |

| 周次 | W1 |
| 依赖 | 无（第一张卡） |

**输入**：本地图片路径（jpg / png，heic 可选）
**输出**：三元组（image, findings, raw_exif）

**工具（逐环节）**

| 环节 | 工具 | 用法 |
|---|---|---|
| 载入 | Pillow / Image.open | 统一转 RGB，记录原始尺寸 |
| 方向矫正 | Pillow / ImageOps.exif_transpose | 手机竖拍不矫正会导致框错位 |
| HEIC | pillow-heif / register_heif_opener | 可选，失败不影响主流程 |
| EXIF 读取 | piexif.load | 取 GPS、DateTimeOriginal、Make、Model、LensModel、BodySerialNumber |
| 缩略图检测 | piexif | 检查 EXIF 内嵌缩略图 IFD（**这里也会藏一张原图**） |
| 坐标归一 | 自写 | 统一成原图像素系，供 A 的检测框对齐 |

**规则表：哪些字段算敏感**

| 字段 | 风险 | 说明 |
|---|---|---|
| GPSLatitude / GPSLongitude | 3 | 精确到米，最危险 |
| DateTimeOriginal | 2 | 可推断作息、住址 |
| Make / Model | 1 | 设备指纹 |
| BodySerialNumber | 2 | 唯一标识，能关联同一人的其他照片 |
| LensModel | 1 | 设备指纹 |
| Software / ProcessingSoftware | 1 | 暴露用了什么修图软件 |
| 内嵌缩略图 | 3 | 打了码但缩略图还是原图，**经典事故** |
| Orientation / ColorSpace / 曝光参数 | 0 | 无害，可保留 |

**验收标准**

- [ ] 对 iPhone 原图，能列出 GPS 经纬度、拍摄时间、机型
- [ ] 对无 EXIF 的 PNG，返回空列表且不报错
- [ ] 竖拍照片经矫正后，用 PIL 画的框位置正确（肉眼不偏）
- [ ] 单元测试覆盖：有 GPS / 无 GPS / 无 EXIF 三种

**降级方案**：HEIC 支持装不上 → 直接不支持 heic，README 写明"请先转 jpg"。

### K-02 元数据清除与图像重建

| 项 | 内容 |
|---|---|
| 负责人 | **B** |
| 人日 | 2 |
| 周次 | W1–W2 |
| 依赖 | K-01 |

**输入**：image + 用户选择（全剥 / 保留时间 / 保留全部无害字段）
**输出**：新文件路径（**必须是新文件，绝不覆盖原图**）

**工具（逐环节）**

| 环节 | 工具 | 用法 |
|---|---|---|
| 重建 | Pillow / Image.new + paste | **从像素重建**，不 copy 原对象的 info |
| 保存 | img.save(..., exif=空) | JPEG quality=92，显式传空 exif |
| ICC 处理 | Pillow | 保留 sRGB profile（否则偏色），不保留其他 |
| 核验 | **ExifTool** exiftool -a -G1 out.jpg | 逐字段打印，作为复检证据 |
| 对比 | 自写 | 比较重建前后像素差（应≈0，只允许 JPEG 压缩误差） |

**关键规则**

1. **不许用"piexif 删字段再存"**——漏字段是必然的（APP13 IPTC、XMP、PNG tEXt、MakerNote）。
2. 一律走「新建画布 → paste → 另存」，这一步同时消灭缩略图和所有非像素数据。
3. 保存后**必须**跑一次 ExifTool，把输出写进日志。

**验收标准**

- [ ] 导出图 exiftool 输出中**不含** GPS、时间、机型、序列号、缩略图
- [ ] 导出图肉眼与原图一致（SSIM > 0.98）
- [ ] 原图未被修改（文件哈希不变）
- [ ] PNG 输入 → PNG 输出时也不残留文本块

**降级方案**：ExifTool 装不上 → 改用 Pillow 读回自身验证，README 注明"未用第三方核验"。

### K-03 OCR 文字检测

| 项 | 内容 |
|---|---|
| 负责人 | **A** |
| 人日 | 3 |
| 周次 | W3–W4 |
| 依赖 | K-01（需要矫正后的图） |

**输入**：image
**输出**：文字块列表，每项含 text、bbox、score（**未分类**的原始结果）

**工具（逐环节）**

| 环节 | 工具 | 用法 |
|---|---|---|
| 主 OCR | **RapidOCR**（onnxruntime 后端） | 调用后返回 box + text + score 三元组 |
| 预处理 | OpenCV | 长边限缩到 **1600px**（再大只慢不准），灰度，CLAHE 增强对比 |
| 小字增强 | OpenCV | 原图 + 2 倍上采样**各跑一次**，结果按 IoU 合并（长文档小字召回靠这招） |
| 后处理 | 自写 | 过滤 score < 0.5，合并同一行相邻 box，去除纯符号 |
| 可视化 | OpenCV rectangle | 调试时把框画出来存图 |

**性能预算**：单张 4000×3000 手机照片，端到端 **≤ 5 秒**（CPU，i5 级）。

**验收标准**

- [ ] 40 张测试集中「正拍清晰」子集（≥15 张）文字块召回 ≥ 85%
- [ ] 单张耗时 ≤ 5s，内存 < 2GB
- [ ] 空图 / 全黑图不崩溃
- [ ] 输出 bbox 坐标系与 K-01 一致（**联调必查，这里最容易错**）

**降级方案**：双尺度太慢 → 只保留 1600px 单尺度，召回下降 5–8 个点，可接受。

### K-04 中文敏感实体识别（6 个模板）

| 项 | 内容 |
|---|---|
| 负责人 | **A** |
| 人日 | 2.5 |
| 周次 | W4 |
| 依赖 | K-03 |

**输入**：文字块列表
**输出**：Finding 列表，kind=text，带 subtype 与 risk

**工具**

| 环节 | 工具 | 用法 |
|---|---|---|
| 正则匹配 | Python re | 每个模板一个预编译 pattern |
| 身份证校验 | 自写约 15 行 | ISO 7064:1983 MOD 11-2，加权因子 + 校验码表 |
| 上下文判断 | 自写 | 检测关键词（"收件人""电话""地址"）是否在 box 附近 ±1 行内 |
| 中文归一 | 自写 | 全角转半角、去空格与连字符（OCR 常把 138 0013 8000 拆开） |

**规则表：6 个模板**

| # | 类型 | 规则 | 风险 | 备注 |
|---|---|---|---|---|
| 1 | 手机号 | 1[3-9] 后接 9 位数字，两侧非数字，允许中间有空格或横线 | 2 | 先归一化再匹配 |
| 2 | 身份证号 | 18 位（末位可 X）+ **MOD 11-2 校验位** | 3 | **校验位是关键**，能把误报从 30% 压到 2% |
| 3 | 快递单号 | 顺丰 SF+12~13 位；通达系 12~14 位纯数字；京东 JD+11~13 位 | 2 | **必须"前缀+长度"双约束**，纯 12 位数字太容易误报 |
| 4 | 地址 | 关键词表（省 / 市 / 区 / 县 / 路 / 街 / 号 / 栋 / 单元 / 室 / 小区）命中 ≥2 个 | 3 | 单命中不算，避免"北京市"这种泛词 |
| 5 | 门牌 / 楼栋 | 数字 + 栋 / 幢 / 号 / 楼，可接单元室 | 3 | 常与地址同时出现，可合成一个框 |
| 6 | 学号 / 准考证号 | 连续 8~14 位数字 + 邻近关键词（学号 / 准考证 / 考号） | 2 | 关键词必需，否则误报爆炸 |

**验收标准**

- [ ] 6 类各有 ≥3 张正样本、≥3 张负样本（负样本用于测误报）
- [ ] 正样本召回 ≥ 80%；负样本误报 ≤ 2 处/张
- [ ] 身份证号：故意篡改 1 位校验位的样本**必须不报**（证明校验位生效）
- [ ] 手机号被 OCR 拆成 138 0013 8000 时仍能识别

**降级方案**：地址 / 学号误报太多 → 直接关掉这两个 subtype（config 开关），只保留 4 类。

### K-05 二维码检测与解码

| 项 | 内容 |
|---|---|
| 负责人 | **A** |
| 人日 | 2 |
| 周次 | W5 |
| 依赖 | K-01 |

**输入**：image
**输出**：Finding 列表，kind=qr，含 payload、bbox、decodable

**工具（双引擎，缺一不可）**

| 环节 | 工具 | 用法 |
|---|---|---|
| 主解码 | **pyzbar** decode() | 支持 QR + 一维条形码，返回 rect + data |
| 兜底定位 | cv2.QRCodeDetector().detect() | pyzbar 解不出时至少给出位置（**标框比不标强**） |
| 预处理 | OpenCV | 灰度 + 自适应二值化 + 放大 2 倍，提升小码成功率 |
| 多码 | pyzbar 天然返回多个 | 逐个处理，不假设只有 1 个 |

**关键规则**

1. **解不出也必须标框**，状态标 decodable=False，文案写"检测到二维码，但无法读取内容"。
2. 一维条形码（快递单上）同样要报，subtype 记为 tracking。
3. 不做"尝试扫描"以外的任何解码（不联网、不调 API）。

**验收标准**

- [ ] 12 张含码测试图，解码成功 ≥ 10 张（≥83%）
- [ ] 解不出的图，bbox 仍然给出且位置正确
- [ ] 一张图有 2 个码时，返回 2 条
- [ ] 无码图不误报（0 误报）

**降级方案**：pyzbar 装不上（zbar DLL 缺失）→ 只用 cv2.QRCodeDetector，解码率降到约 60%，但流程不断。

### K-06 二维码内容分类（差异化功能 · 便宜且抓眼）

| 项 | 内容 |
|---|---|
| 负责人 | **A** |
| 人日 | 1.5 |
| 周次 | W5 |
| 依赖 | K-05 |

**输入**：payload 字符串
**输出**：三元组（subtype, risk, 一句话说明），回填进 Finding

**工具**

| 环节 | 工具 | 用法 |
|---|---|---|
| 字符串判定 | Python re / startswith | 纯规则，**不联网、不解析跳转** |
| 域提取 | urllib.parse.urlparse | 只取 host，用于展示"跳转到 xx.com" |
| Wi-Fi 解析 | 自写 | 解析 WIFI:S:ssid;T:WPA;P:pass;; 中的 SSID |
| vCard 解析 | 自写极简版 | 只取 FN 与 TEL 两行，不做完整解析 |

**规则表（照抄即可）**

| payload 特征 | subtype | 展示文案 | risk |
|---|---|---|---|
| https://u.wechat.com/... | wechat_card | 微信个人名片，扫了能直接加好友 | 3 |
| https://weixin.qq.com/g/... | wechat_group | 微信群邀请码 | 2 |
| wxp://... | wechat_pay | 微信收款码，通常绑定实名 | 3 |
| https://qr.alipay.com/... 或 alipays:// | alipay | 支付宝收款/付款码 | 3 |
| WIFI:S:...;T:...;P:...;; | wifi | **Wi-Fi 密码，扫一下就能连上** | 3 |
| BEGIN:VCARD 或 mecard: | vcard | 联系人名片，含姓名和电话 | 3 |
| tel: / sms: / mailto: | contact | 直接拨号或发信 | 2 |
| geo: | geo | 地理坐标，直接暴露位置 | 3 |
| 纯数字或 ≤8 位短码 | code | 可能是取件码 / 会员码 / 票号 | 2 |
| 其他 http(s):// | link | 跳转到某个域名（离线不展开短链） | 1 |
| 其他 | unknown | 无法识别类型 | 1 |

**三条红线（写进 README）**

1. **不联网**，所以短链（t.cn / dwz.cn）**看不到终点**，文案必须写"短链接，离线无法展开"。
2. **微信码是不透明 ID**，只能判断"这是微信名片"，**不能**判断是谁。
3. 不展示 payload 全文（可能是别人的隐私），只展示类型 + 关键字段（域名 / SSID）。

**验收标准**

- [ ] 12 种类型各 1 张样本，分类准确率 100%（规则题，应该满分）
- [ ] Wi-Fi 码能显示出 SSID
- [ ] 短链正确显示"无法离线展开"，不是瞎猜域名
- [ ] 全模块无任何网络 import（grep 不到 requests / urllib.request / socket）

**降级方案**：时间不够 → 只保留 5 类（微信名片 / 收款码 / Wi-Fi / 名片 / 普通链接），覆盖 90% 场景。

**验收标准**

- [ ] 正脸召回 ≥ 85%（20 张人像测试集）
- [ ] 侧脸 / 口罩允许漏，但**不得报错**
- [ ] 一张 10 人合影能框出 ≥ 8 张
- [ ] 全项目 grep 不到 face_recognition / arcface / embedding

**降级方案**：mediapipe 装不上 → 用 cv2.FaceDetectorYN；再不行 → 只保留"手动框选"（功能降级但可用）。

| 依赖 | K-01, K-03, K-05, K-07（拿到 bbox） |

**输入**：image + 用户勾选后的 Finding 列表
**输出**：脱敏后的 image（内存对象，交给 K-02 导出）

**工具**

| 环节 | 工具 | 用法 |
|---|---|---|
| 区域裁剪 | OpenCV / NumPy 切片 | 按 bbox 取 ROI |
| 模糊 | cv2.GaussianBlur | kernel 按 ROI 短边 **≥ 1/4** 自适应，**不许固定 15** |
| 马赛克 | cv2.resize 缩小再放大 | 先缩到 1/20 再放大，用 INTER_NEAREST |
| 纯色 | NumPy 填充 | 默认黑色，可配置 |
| 边界外扩 | 自写 | bbox 统一外扩 **6px**，防止边缘泄露笔画 |
| 性能 | NumPy 向量化 | 不要 Python 循环逐像素 |

**关键规则（这是本卡真正的技术点）**

1. **模糊核必须与区域尺寸挂钩**。固定 kernel=15 在 4K 图上等于没遮，在 200px 小图上等于糊成一片。
2. **必须外扩**。OCR 的 bbox 常常比文字实际范围小 1–3px，不外扩就会露笔画。
3. **不做"贴图覆盖"**，一律在像素上重算，然后走 K-02 重建导出。

**验收标准**

- [ ] 三种方式都能用，效果肉眼可见且不破坏画面其他部分
- [ ] 遮住的文字区块，用同参数 OCR 重跑**读不出原文**（≥ 9/10 张）
- [ ] 遮住的二维码，pyzbar 重跑**解不出**（≥ 9/10 张，**注意 QR 有 30% 纠错，必须整块盖**）
- [ ] 4K 图处理耗时 < 1s

**降级方案**：马赛克效果不达标 → 直接禁用该选项，只留模糊 + 纯色（少一个选项而已）。

### K-09 复检器（**本项目的核心卡**）

| 项 | 内容 |
|---|---|
| 负责人 | **B** |
| 人日 | 2.5 |
| 周次 | W8 |
| 依赖 | K-02, K-03, K-04, K-05, K-07 |

**输入**：导出的新文件
**输出**：Verdict 结构

**工具**

| 检查项 | 工具 | 判定方式 |
|---|---|---|
| EXIF | **ExifTool** + piexif | 敏感字段数为 0 → ok |
| 二维码 | pyzbar 重跑 | 所有码 decodable=False → ok；**能解出 → 直接 fail** |
| 文字 | RapidOCR 重跑 + K-04 规则 | 残留 Finding 数 = 0 → ok |
| 人脸 | mediapipe 重跑 | **仅当用户选择"遮人脸"时**检查；未选则跳过 |
| 结构 | Pillow | 能正常打开、尺寸未变、非全黑（防覆盖过度） |

**关键设计原则**

1. 复检**必须用独立于处置流程的代码路径**（不能复用同一个中间变量，否则等于自己检查自己）。
2. 复检结果**只报告事实**，不做"已确保安全"的承诺。文案固定为"复检发现 N 项残留"。
3. **人脸检查是条件触发**：用户选择保留人脸时，复检不能判 fail（否则逻辑矛盾）。

**验收标准**

- [ ] 对「完全没处理」的原图跑复检，必须判 **fail**（证明它不是永远返回通过）
- [ ] 对「正确处理」的图，判 pass
- [ ] 故意只遮二维码左半边 → 复检必须抓出来（**这条最能体现价值**）
- [ ] 复检总耗时 < 8s
- [ ] 4 个 check 项的结果都能单独显示（不是笼统一个通过）

**降级方案**：OCR 复检太慢 → 只对"用户勾选过的区域"做局部复检，不做全图。
